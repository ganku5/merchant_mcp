# Web Mandate API Integration Guide

Source endpoint: `POST /api/{apiVersion}/merchants/mandates/webMandate`

## Overview

Web Mandate is a merchant server-to-server API used to create a payee-initiated UPI mandate collect request.

The merchant calls this API with mandate details such as amount, payer VPA, validity, recurrence, expiry, and optional TPV, first-execution, split-settlement, or sub-merchant details. Newton verifies the S2S envelope, applies merchant defaults, validates mandate business rules, stores validation data where required, sends the create request to the mandate wrapper, and returns the created mandate identifiers and gateway response fields.

This route creates an outgoing/payee mandate request. The API response envelope can be `SUCCESS` while the mandate request is still awaiting customer authorization. Clients must use `payload.gatewayResponseStatus`, `payload.gatewayResponseCode`, and `payload.gatewayResponseMessage` as the mandate creation outcome.

## Business Use Case

Use this API when the merchant backend needs to initiate a UPI mandate collect from a customer VPA, for example:

- Subscription setup where the customer receives a mandate authorization request in a UPI app.
- One-time block or one-time debit authorization.
- Recurring debit authorization with weekly, monthly, quarterly, yearly, or as-presented schedules.
- IPO or similar collect journeys where `refId`, `refCategory`, and `refUrl` carry merchant reference data.
- TPV mandate creation where the mandate must be tied to expected payer account hashes.
- Mandate creation with an automatic first execution when the merchant is enabled for that feature.
- Dynamic VPA or aggregator journeys where the request payee VPA and sub-merchant details are validated against merchant configuration.

Do not use this API to create a payer-side mandate from a stored customer account, execute an existing mandate, notify an execution cycle, pause/unpause a mandate, update a mandate, or check mandate status. Those are separate mandate APIs.

## Integration Flow

1. Merchant creates a unique mandate order/reference in its own system.
2. Merchant sends an encrypted or signed S2S request with the mandate details and a unique `merchantRequestId`. `upiRequestId` may be supplied by the merchant or generated by Newton when omitted.
3. Newton unwraps the request envelope and verifies merchant headers, API access, timestamp, signature, and optional IP allowlist.
4. Newton resolves the master merchant or sub-merchant, loads the primary merchant account, applies defaults, and validates field formats.
5. Newton validates mandate recurrence, purpose, block-fund, revocability, dates, amount limits, dynamic VPA requirements, platform restrictions, duplicate mandate ids, and first-execution rules.
6. If configured, Newton registers TPV, split-settlement, or first-execution validation data before creating the mandate.
7. Newton creates the mandate through the mandate wrapper and returns gateway identifiers and gateway status fields.
8. Merchant stores `merchantRequestId`, `gatewayMandateId`, `orgMandateId`, `gatewayResponseStatus`, and reconciliation metadata, then follows final status through callbacks or mandate status APIs.

Important identifiers:

- `merchantRequestId`: Merchant-generated idempotency/order reference. A duplicate mandate for the same merchant and PAYEE role is rejected.
- `upiRequestId`: UPI mandate request id. If omitted, Newton generates one before duplicate validation and returns it as `gatewayMandateId` and `orgMandateId`.
- `gatewayMandateId`: The UPI request id used for the create request.
- `orgMandateId`: The mandate's stored UPI request id. For this route it matches `gatewayMandateId`.
- `refId`: Optional merchant reference. IPO-style flows can reuse the same `refId` across different `merchantRequestId` values.

## Handler Path

The route is mounted under `/api/{apiVersion}` in the main `ServerToServerAPIs` group.

The request path is:

1. `getReqBody` calls `merchantPayloadVerificationS2S` to identify the merchant from headers and unwrap plain, JWS, or JWE payloads.
2. `merchantSignatureVerificationV2` validates `iat` for signed/encrypted bodies, merchant headers, API allow/block configuration, merchant customer context when applicable, request timestamp, header signature for plain payloads, and optional IP allowlist.
3. `webMandateTransformerRoute` transforms the S2S request to the core request. If `upiRequestId` is absent, Newton generates one.
4. `webMandateRoute` validates the core request, resolves merchant/sub-merchant and merchant account data, applies defaults, checks API version restrictions, validates business rules, registers TPV or first-execution data, invokes the mandate wrapper, and builds the core response.
5. `mkWebMandateResponseS2S` maps the core response back to the S2S response.
6. `flowWithTrace` returns the response using the merchant response strategy.

## Authentication and Payload Handling

The route request type is `EncRequest WebMandateRequest`. Depending on merchant configuration, the wire request can be:

- JWE encrypted payload containing a signed payload.
- JWS signed payload.
- Plain decrypted JSON payload accepted only where merchant configuration permits it and protected by `x-merchant-signature`.

For signed or encrypted request bodies, the decrypted business payload must include `iat`, and `iat` must pass timestamp validation. Plain-body header-signature mode does not validate request-body `iat`, but still requires merchant headers, `x-timestamp`, raw-body capture, and a valid header signature.

The response is returned according to the merchant response strategy configured during onboarding. The examples in this guide are decrypted response bodies, not the exact encrypted wire envelope.

### Recurrence Rules

| Pattern | `recurrenceRule` | `recurrenceValue` | Notes |
| --- | --- | --- | --- |
| `ONETIME` | Must be omitted. | Must be omitted. | Validity duration must be 90 days or less. Purpose must be omitted, `00`, `01`, or `14`. |
| `DAILY` | Usually omitted. | Usually omitted. | General recurrence validation still applies in shared helpers. |
| `WEEKLY` | Required. | Required; `1` to `7`. | Code has an explicit weekly guard before shared recurrence validation. |
| `FORTNIGHTLY` | Required. | Required; shared helper validates range. | Send according to onboarding rules. |
| `MONTHLY`, `BIMONTHLY`, `QUARTERLY`, `HALFYEARLY`, `YEARLY` | Required. | Required; shared helper validates range. | Commonly use day of period values such as `1` to `31`. |
| `ASPRESENTED` | Depends on shared helper rules. | Depends on shared helper rules. | Use only when enabled for the merchant. |

### Gateway Status Interpretation

For PAYEE/web mandate creation:

| Stored mandate state | Response mapping |
| --- | --- |
| Mandate stored as `SUCCESS` | `gatewayResponseCode: "00"`, `gatewayResponseMessage: "Mandate Creation Success"`, `gatewayResponseStatus: "SUCCESS"`. |
| Mandate stored as `PENDING` | `gatewayResponseCode: "00"`, `gatewayResponseMessage: "Mandate Create Request Sent Successfully"`, `gatewayResponseStatus: "SUCCESS"`. |
| Any failure state | Response code comes from NPCI/wrapper response when available, otherwise `JPNL`; message comes from wrapper result when available, otherwise `Mandate Request Failed`; status is `FAILURE`. |

## Error Handling

Failure responses use the same response transport as success responses when the request reaches response wrapping. Authentication, signature, decryption, and early parsing failures can be returned before a normal encrypted business response is possible. After decryption, error bodies generally follow Newton's shared error shape:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "RegexValidation \"amount regex match failed\"",
  "payload": null
}
```

HTTP status is not a reliable business-status signal for all branches: some validation failures are thrown with HTTP 200 and an error body, while other business validation failures use HTTP 400. Always parse the decrypted body.

### Validation Failures

Example invalid amount format:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "RegexValidation \"amount regex match failed\"",
  "payload": null
}
```

Example invalid recurrence:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "Mandate Recurrence Rule must be present and Mandate Recurrence Rule value in between 1 to 7 for WEEKLY pattern",
  "payload": null
}
```

Client handling: fix the request and do not retry unchanged. Common validation causes include invalid amount format, invalid VPA, invalid `merchantRequestId` or `upiRequestId`, invalid expiry, invalid dates, malformed `udfParameters`, empty `payerAccountHashes`, invalid `tpvType`/`platform`, invalid sub-merchant enums, or invalid recurrence rule/value combinations.

### Auth, Signature, Encryption, and Timestamp Failures

Missing headers, invalid merchant ids, failed JWS signature verification, failed JWE decryption, invalid header signature, invalid `iat`, invalid `x-timestamp`, or missing raw body for signature verification can return:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "UNAUTHORIZED",
  "payload": null
}
```

If the encrypted/signed payload cannot be parsed, the body can instead be:

```json
{
  "status": "FAILURE",
  "responseCode": "INVALID_DATA",
  "responseMessage": "Error in $: key \"payload\" not found",
  "payload": null
}
```

Client handling: do not retry unchanged. Check headers, key id, signing/encryption mode, timestamp freshness, body canonicalization, and whether `iat` is present for signed/encrypted calls.

### Merchant Configuration, API Disabled, and IP Restriction

If the API is blocked or not allowed for the merchant:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "API NOT ENABLED",
  "payload": null
}
```

If the merchant has IP allowlisting and `x-forwarded-for` is missing or not allowlisted:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "UNAUTHORIZED",
  "payload": null
}
```

Client handling: contact onboarding/support to enable the API or update merchant allowlists/configuration. Retrying the same request will not help.

### Lookup Failures

Merchant, sub-merchant, merchant account, key-store, merchant configuration, or default account lookups can fail before product logic completes. The exact message varies by helper and deployment, but the decrypted body usually uses `BAD_REQUEST`, `UNAUTHORIZED`, or `INTERNAL_SERVER_ERROR`.

Example:

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR",
  "payload": null
}
```

Client handling: verify merchant headers and onboarding setup. If headers are correct, treat as configuration/support issue and use `x-request-id` for investigation.

### Duplicate Request

Newton rejects a request if an existing PAYEE mandate is found for the same `merchantRequestId` and merchant, or if the `upiRequestId` already exists.

```json
{
  "status": "FAILURE",
  "responseCode": "DUPLICATE_REQUEST",
  "responseMessage": "DUPLICATE_REQUEST",
  "payload": null
}
```

Client handling: do not create a new mandate with the same identifiers. Query mandate status using the original identifiers, or create a new mandate with a new `merchantRequestId` and `upiRequestId` only if this is truly a new customer authorization.

### Downstream Gateway or Wrapper Failures

If the mandate wrapper returns no mandate object:

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR",
  "payload": null
}
```

If the wrapper returns timeout code `U09`:

```json
{
  "status": "FAILURE",
  "responseCode": "GATEWAY_TIMEOUT",
  "responseMessage": "Timed out from NPCI",
  "payload": null
}
```

If the wrapper marks the call as an error:

```json
{
  "status": "FAILURE",
  "responseCode": "SERVICE_UNAVAILABLE_NPCI_U09",
  "responseMessage": "NPCI service is not reachable at the moment (U09)",
  "payload": null
}
```

The `U09` suffix is a representative timeout code; Newton can use another downstream code or `NA` when no specific code is available.

Client handling: retry only with the same `merchantRequestId`/`upiRequestId` after checking status or after the advised retry window. If a retry returns `DUPLICATE_REQUEST`, reconcile using status APIs or callbacks instead of creating a new mandate.

### Unexpected Errors

Unexpected parsing, configuration, database, or wrapper failures can return:

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR",
  "payload": null
}
```

Client handling: treat as unknown outcome if the request passed authentication and duplicate validation may have occurred. Query mandate status by `merchantRequestId` or `upiRequestId` before creating another mandate.

## Retry and Idempotency Guidance

- Use a stable `merchantRequestId` for one business mandate creation attempt.
- Supply a stable `upiRequestId` if your system generates UPI ids; otherwise store the generated id from the first successful response.
- Do not retry validation, auth, API-disabled, IP restriction, or merchant-configuration failures unchanged.
- For network timeouts or `SERVICE_UNAVAILABLE`/`GATEWAY_TIMEOUT`, retry with the same identifiers after checking whether a mandate was created.
- If a retry returns `DUPLICATE_REQUEST`, treat the original request as accepted or already present and reconcile through status/callbacks.
- Create a new `merchantRequestId` and `upiRequestId` only for a new customer authorization attempt, not for blind retries.
- Store `gatewayResponseStatus` separately from API `status`; a successful API envelope does not guarantee final customer authorization.
