# Fetch Credit Card Bill API Integration Guide

Source endpoint: `POST /api/{apiVersion}/merchants/creditCard/fetchBill`

## Overview

Fetch Credit Card Bill is a Newton server-to-server API for retrieving the latest credit-card bill details available through the UPI credit-card bill fetch rail.

The merchant calls this API for an onboarded Newton customer and bound device. Newton validates the merchant, customer, device fingerprint, and credit-card input, builds an NPCI `ReqCCBill` request, and returns the bill details from NPCI when the issuer/card supports bill fetch.

Use this API when the merchant backend needs to show a customer's card bill, due date, minimum amount due, total amount due, late fee, interest rate, or billing period before the customer proceeds with payment or related credit-card servicing.

## Business Use Case

Fetch Credit Card Bill helps merchants:

- Fetch bill details for a credit card already linked to the Newton customer profile.
- Fetch bill details for an unlinked credit card by collecting the customer's issuing-bank code, linked mobile number, and last four card digits.
- Validate the customer/device context before sending the bill fetch request to NPCI.
- Display issuer-provided bill information before starting a payment, EMI, or servicing journey.
- Preserve a merchant-side audit trail with `upiRequestId`, `merchantCustomerId`, and optional `udfParameters`.

Supported request modes:

| Mode | `isCCAccLinked` | Use when | NPCI subtype |
| --- | --- | --- | --- |
| Linked credit card | `"true"` | The customer has a Newton-linked credit-card account and the merchant has its `bankAccountUniqueId`. | `SELF` |
| Unlinked credit card | `"false"` | The customer wants to fetch a card bill using bank/mobile/card details without selecting a linked Newton account. | `OTHERS` |

## Integration Flow

1. Merchant identifies the Newton `merchantCustomerId` and the active device fingerprint for the customer.
2. Merchant chooses linked-card or unlinked-card mode.
3. Merchant calls `fetchBill` with a fresh `upiRequestId`.
4. Newton decrypts/verifies the request, checks merchant API access, validates the customer context, and verifies the device fingerprint.
5. For linked mode, Newton resolves `creditAccDetails.bankAccountUniqueId` to an active credit-card account. For unlinked mode, Newton validates the supplied bank/mobile/card details.
6. Newton generates the credit-card VPA, for example `CC.919876543210@hdfcbank`, and sends `ReqCCBill` to NPCI.
7. Merchant decrypts/verifies the response and uses `payload.gatewayResponseStatus` and `payload.gatewayResponseCode` to decide whether bill details were fetched.

Important identifiers:

- `upiRequestId`: Merchant-generated transaction id for this bill fetch. It is sent to NPCI as the transaction id.
- `merchantCustomerId`: Merchant's customer identifier registered with Newton. It is also used during signature verification context setup.
- `bankAccountUniqueId`: Account mapping identifier required only for linked-card fetches.
- `ccVpa`: Credit-card VPA generated by Newton and returned only on gateway success.

## Authentication and Encryption

Newton accepts the S2S encrypted/signed envelope configured during onboarding:

- `JWS_AND_JWE`: request body is encrypted as JWE and contains a signed JWS payload.
- `JWS`: request body is a signed JWS payload.
- Legacy/plain integrations: request body is plain JSON and must be protected by the configured merchant signature headers.

For JWS/JWE requests, include `iat` in the decrypted business payload. The route validates `iat` and `x-timestamp` as 13-digit epoch millisecond timestamps within the accepted freshness window.

Responses use the corresponding configured response protection. Legacy/plain response mode includes an `X-Response-Signature` header. JWS/JWE response mode returns a signed or encrypted body instead.

```json

  "merchantCustomerId": "CUST12345",
  "deviceFingerPrint": "device-fingerprint-hash",
  "isCCAccLinked": "false",
```

### Field Reference

| Field | Type | Required | Default / omitted behavior | Description |
| --- | --- | --- | --- | --- |
| `upiRequestId` | string | Yes | No default. | Merchant-generated id for this bill fetch. Must be 1 to 35 alphanumeric characters. |
| `merchantCustomerId` | string | Yes | No default. | Merchant customer id registered with Newton. Must match the authenticated merchant customer context. Max 256 characters. |
| `deviceFingerPrint` | string | Yes | No default. | Device fingerprint for the bound customer device. Must match the stored fingerprint, unless `fallbackDeviceFingerPrint` matches. |
| `fallbackDeviceFingerPrint` | string | No | No default. | Alternate fingerprint accepted for device match checks. |
| `payerVpa` | string | No | If omitted, Newton builds a default payer VPA from the customer's mobile number and the merchant/default VPA domain. | Customer/payer VPA sent to NPCI. Must be a valid VPA when supplied. |
| `payeeVpa` | string | No | The bill-fetch flow generates the downstream payee VPA internally. Omit unless Newton specifically asks for it during onboarding/testing. | Optional credit-card VPA field validated as a value such as `CC.919876543210@hdfcbank` when supplied. |
| `isCCAccLinked` | string | Yes | No default. | `"true"` for linked-card fetch; `"false"` for unlinked-card fetch. Case-insensitive validation accepts true/false strings. |
| `creditAccDetails` | object | Yes | No default. | Credit-card account details. Conditional requirements depend on `isCCAccLinked`. |
| `udfParameters` | string | No | Omitted from response when absent. | JSON-object string for merchant metadata. Echoed in the response when supplied. |
| `iat` | string | Conditional | Required for JWS/JWE requests. Not required for plain payload mode. | Issued-at timestamp used by S2S request freshness validation. Use 13-digit epoch milliseconds. |
| `remarks` | string | No | If omitted, Newton sends `ReqCCBill` as the NPCI note. | Customer/merchant-facing note. Must be 1 to 255 characters when supplied. |

### `creditAccDetails`

| Field | Type | Required | Default / omitted behavior | Description |
| --- | --- | --- | --- | --- |
| `bankAccountUniqueId` | string | Conditional | No default. | Required when `isCCAccLinked = "true"`. Must be omitted when `isCCAccLinked = "false"`. Resolves to the customer's linked credit-card account. |
| `bankCode` | string | Conditional | For linked mode, Newton uses the resolved account's bank code. | Required when `isCCAccLinked = "false"`. Must be omitted when `isCCAccLinked = "true"`. Numeric bank IIN/code, max 20 characters. |
| `countryCode` | string | No | If omitted, `linkedMobileNumber` is treated as a domestic 10-digit mobile number. | Optional country code for `linkedMobileNumber`. Max 7 characters, optional leading `+`, digits only. |
| `linkedMobileNumber` | string | Conditional | For linked mode, Newton uses the customer's stored mobile number. | Required when `isCCAccLinked = "false"`. Must be omitted when `isCCAccLinked = "true"`. Domestic mobile must be exactly 10 digits when `countryCode` is omitted; with `countryCode`, length must be less than 19 and numeric. |
| `cardDigits` | string | Conditional | No default. | Required when `isCCAccLinked = "false"`. Must be omitted when `isCCAccLinked = "true"`. Last four card digits; exactly 4 numeric characters. |

### Conditional Rules

| `isCCAccLinked` | Required fields | Must not send |
| --- | --- | --- |
| `"true"` | `creditAccDetails.bankAccountUniqueId` | `creditAccDetails.bankCode`, `creditAccDetails.linkedMobileNumber`, `creditAccDetails.cardDigits` |
| `"false"` | `creditAccDetails.bankCode`, `creditAccDetails.linkedMobileNumber`, `creditAccDetails.cardDigits` | `creditAccDetails.bankAccountUniqueId` |

`countryCode` is only meaningful with unlinked-card `linkedMobileNumber`. The downstream payee VPA is generated from mobile number and bank handle.

### Validation Notes

Newton applies both request-shape validation and bill-fetch-specific business validation:

- `upiRequestId`: 1 to 35 alphanumeric characters.
- `merchantCustomerId`: non-empty, max 256 characters, restricted character set.
- `deviceFingerPrint`, `fallbackDeviceFingerPrint`, and `bankAccountUniqueId`: non-empty when supplied/required.
- `payerVpa`: valid VPA format, 3 to 255 characters.
- `payeeVpa`: credit-card VPA format such as `CC.919876543210@hdfcbank`, 17 to 255 characters, when supplied.
- `isCCAccLinked`: string `"true"` or `"false"`.
- `bankCode`: numeric, max 20 characters.
- `countryCode`: digits with optional leading `+`, max 7 characters.
- `linkedMobileNumber`: domestic 10 digits when `countryCode` is omitted; less than 19 digits for international/mobile-with-country-code use.
- `cardDigits`: exactly 4 digits.
- `remarks`: 1 to 255 characters, letters/numbers/spaces/hyphen.
- `udfParameters`: must be a JSON-object string and must pass text character validation.
- The API must be enabled for the merchant; blocked or unallowed API configuration fails before product logic.
- The `merchantCustomerId` must belong to the authenticated merchant/channel.
- The device fingerprint or fallback fingerprint must match the customer's bound device.
- In linked mode, the resolved account must be a credit-card/`CREDIT` account.

## Response

### Response Envelope

| Field | Type | Description |
| --- | --- | --- |
| `status` | string | Newton API processing status. For a processed downstream response, this is `SUCCESS` even when NPCI/business status is failure. |
| `responseCode` | string | Newton response code. Success value is `SUCCESS`. |
| `responseMessage` | string | Newton response message. Success value is `SUCCESS`. |
| `payload` | object | Bill-fetch result. |
| `udfParameters` | string | Echoed from request when supplied. Omitted when not supplied. |

### Payload Fields

| Field | Type | Description |
| --- | --- | --- |
| `gatewayResponseStatus` | string | Downstream bill-fetch result status, usually `SUCCESS` or `FAILURE`. Use this field, not only top-level `status`, to decide whether bill details were fetched. |
| `gatewayResponseCode` | string | NPCI/downstream response code. Defaults to `00` only when no downstream code is available. |
| `gatewayResponseMessage` | string | `Your Fetch CC bill call is successful.` when `gatewayResponseCode` is `00`; otherwise the mapped downstream message. |
| `merchantId` | string | Merchant id configured with Newton. |
| `merchantChannelId` | string | Merchant channel id configured with Newton. |
| `merchantCustomerId` | string | Merchant customer id supplied in the request. |
| `ccVpa` | string | Generated credit-card VPA used as downstream payee. Returned only on gateway success. |
| `billDetails` | object | Bill details mapped from NPCI `BillData`. Returned only on gateway success. The object can be present with only the fields provided by the issuer. |

### `billDetails`

| Field | Type | Description |
| --- | --- | --- |
| `regName` | string | Registered cardholder/name value returned by NPCI, when available. |
| `dueDate` | string | Payment due date returned by issuer/NPCI. |
| `billDate` | string | Bill generation date returned by issuer/NPCI. |
| `minDueAmt` | string | Minimum due amount. |
| `totalDueAmt` | string | Total due amount. |
| `latePaymentFee` | string | Late payment fee, if returned. |
| `interestRate` | string | Interest rate, if returned. |
| `billingPeriod` | string | Billing period, if returned. |

### Business Failure Returned in a Success Envelope

NPCI can return a business failure after Newton has successfully processed the API call. In that case the top-level status remains `SUCCESS`, while `payload.gatewayResponseStatus` is `FAILURE`. `ccVpa` and `billDetails` are omitted.

```json
{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "gatewayResponseStatus": "FAILURE",
    "gatewayResponseCode": "C1",
    "gatewayResponseMessage": "Credit card does not exist",
    "merchantId": "MERCHANT123",
    "merchantChannelId": "CHANNEL123",
    "merchantCustomerId": "CUST12345"
  }
}
```

## Response Interpretation

- Treat top-level `status = "FAILURE"` as a Newton/API failure. The bill fetch was not completed successfully.
- Treat top-level `status = "SUCCESS"` with `payload.gatewayResponseStatus = "SUCCESS"` and `payload.gatewayResponseCode = "00"` as a successful bill fetch.
- Treat top-level `status = "SUCCESS"` with `payload.gatewayResponseStatus = "FAILURE"` as a completed bill-fetch attempt with a downstream/business decline.
- Do not infer bill-fetch success from the top-level `status` alone.
- Use `billDetails` only when `payload.gatewayResponseStatus = "SUCCESS"`. If a field inside `billDetails` is omitted, the issuer/NPCI did not return that field.

## Error Handling

Failure responses use the same S2S response protection as success responses. The examples below show decrypted response bodies. When `payload` is empty, it is omitted.

Depending on where validation fails, the HTTP status can be `200`, `400`, `401`, or `500`; clients should read `status`, `responseCode`, and `responseMessage` from the decrypted body.

### Failure Scenarios

| Scenario | Example decrypted response body | Client handling |
| --- | --- | --- |
| Request field validation fails, such as invalid `upiRequestId`, empty `deviceFingerPrint`, invalid `payerVpa`, invalid `payeeVpa`, invalid `isCCAccLinked`, invalid `cardDigits`, invalid remarks, or invalid `udfParameters` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"RegexValidation \"upiRequestId regex match failed\""}` | Fix the request. Do not retry unchanged. |
| Linked mode omits `bankAccountUniqueId` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Account-Id is required in case of isCCAccLinked = True"}` | Send the linked credit-card account identifier returned by Newton. |
| Linked mode also sends unlinked-card fields | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Linked-Mobile-Number, Bank-Code, Card-Digits should not be provided if Account-Id is present and isCCAccLinked = True"}` | Remove `bankCode`, `linkedMobileNumber`, and `cardDigits` for linked-card fetch. |
| Unlinked mode sends `bankAccountUniqueId` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Account-Id is not required when isCCAccLinked is False"}` | Remove `bankAccountUniqueId`; send bank/mobile/card fields. |
| Unlinked mode omits `bankCode`, `linkedMobileNumber`, or `cardDigits` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Linked-Mobile-Number, Bank-Code, Card-Digits is required when isCCAccLinked = False"}` | Send all three unlinked-card fields. |
| Missing or stale `iat`/`x-timestamp` for signed/encrypted requests | `{"status":"FAILURE","responseCode":"REQUEST_EXPIRED","responseMessage":"REQUEST_EXPIRED"}` | Regenerate the timestamp, signature/envelope, and request. |
| Timestamp is not a 13-digit epoch millisecond value | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Timestamp must be a 13-digit number"}` | Fix timestamp generation. |
| JWS verification, JWE decryption, missing key id/private key, or malformed protected payload fails | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` | Check keys, `kid`, encryption mode, body canonicalization, and onboarding configuration. |
| Legacy/plain signature headers are missing or signature verification fails | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` | Recompute signature over the exact request body and timestamp. |
| Merchant configuration blocks or does not allow `fetchCCBillS2S` | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"API NOT ENABLED"}` | Enable the API for the merchant/channel before retrying. |
| Merchant IP allowlist rejects the request | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` | Call from an allowlisted IP or update merchant configuration. |
| `merchantCustomerId` does not match the authenticated merchant customer context | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Invalid merchantCustomerId"}` | Use the customer id registered under the same merchant/channel. |
| Device id is missing on the merchant customer record or device lookup/decryption fails | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Invalid DeviceId cannot be null for merchantCustomer"}` or `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` | Re-bind/recover the customer device before retrying. |
| Device fingerprint does not match the bound device | `{"status":"FAILURE","responseCode":"DEVICE_FINGERPRINT_MISMATCH","responseMessage":"DEVICE_FINGERPRINT_MISMATCH"}` | Send the active device fingerprint or fallback fingerprint. |
| Linked `bankAccountUniqueId` is not linked to the merchant customer or account lookup fails | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Account not found"}` | Refresh linked accounts and use the credit-card account mapping returned by Newton. |
| Linked account is not a credit-card account | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Account type should be CREDIT"}` | Use a linked credit-card account. |
| Unlinked `bankCode` does not resolve to a configured bank/IIN or bank handle cannot be found | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"bankHandle not found for bankCode"}` | Use a supported credit-card issuing bank code from Newton onboarding/list-bank guidance. |
| NPCI returns a bill-fetch business failure, such as card not found, issuer bill fetch failure, invalid card, or issuer system error | `{"status":"SUCCESS","responseCode":"SUCCESS","responseMessage":"SUCCESS","payload":{"gatewayResponseStatus":"FAILURE","gatewayResponseCode":"C2","gatewayResponseMessage":"System Error/Bill fetch Failure","merchantId":"MERCHANT123","merchantChannelId":"CHANNEL123","merchantCustomerId":"CUST12345"}}` | Treat as a completed business/downstream decline. Retry only if the code/message is operationally retryable for your journey. |
| NPCI immediate error returns a mapped error code rather than timing out | `{"status":"SUCCESS","responseCode":"SUCCESS","responseMessage":"SUCCESS","payload":{"gatewayResponseStatus":"FAILURE","gatewayResponseCode":"U09","gatewayResponseMessage":"NPCI service is not reachable at the moment (U09)","merchantId":"MERCHANT123","merchantChannelId":"CHANNEL123","merchantCustomerId":"CUST12345"}}` | Retry only if the code is known to be transient for your integration. |
| NPCI is unreachable or the bill-fetch request times out | `{"status":"FAILURE","responseCode":"SERVICE_UNAVAILABLE_NPCI_U09","responseMessage":"NPCI service is not reachable at the moment (U09)"}` | Retry with bounded backoff if the customer is still in the journey. |
| NPCI returns an unexpected result value | `{"status":"FAILURE","responseCode":"INVALID_NPCI_RESULT","responseMessage":"Unexpected result from NPCI in RespCCBill: QUEUED"}` | Treat as technical failure and escalate with `upiRequestId`. |
| Decode failure, missing async response, database/cache/encryption failure, or other unexpected server failure | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` | Retry transiently with backoff; escalate if persistent. |

## Retry, Idempotency, and Client Handling

`fetchBill` does not use a separate `merchantRequestId` idempotency key. The request `upiRequestId` is the transaction id sent to NPCI.

Recommended handling:

- Generate a unique `upiRequestId` for each logical bill-fetch attempt and store it with the merchant order/customer/card context.
- Do not reuse a successful `upiRequestId` for a different customer, card, bank code, mobile number, or linked account.
- If the client receives a decrypted response, handle it by body status. Do not retry top-level `SUCCESS` with `payload.gatewayResponseStatus = "FAILURE"` unless the failure code is known to be transient or the customer changes the request context.
- Retry network failures, client timeouts with no decrypted body, `SERVICE_UNAVAILABLE_NPCI_*`, and transient `INTERNAL_SERVER_ERROR` with exponential backoff and jitter.
- Because there is no explicit idempotency record for this API, repeated retries can result in another downstream `ReqCCBill` attempt. Avoid rapid retry loops.
- Do not retry validation, authentication, merchant-configuration, account, bank-code, or device-fingerprint failures without correcting the underlying data.
