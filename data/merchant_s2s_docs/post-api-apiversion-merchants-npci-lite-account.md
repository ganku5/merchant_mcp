# UPI Lite Account Params API Integration Guide

Source endpoint: `POST /api/{apiVersion}/merchants/npci/lite/account`

## Overview

The UPI Lite Account Params API is a server-to-server API used to fetch the NPCI Lite account key material and Lite Reference Number (LRN) required during UPI Lite account creation or activation.

The merchant backend calls this API after the customer, device, and bank account are already known to Newton. Newton validates the merchant request envelope and signature, resolves the merchant customer, device, and account records, validates the customer's UPI Lite account state, extracts the `identitycred` from the credential block generated by the client library, calls NPCI `ReqListKeys` with transaction type `GetLite`, and returns the raw NPCI `RespListKeys` XML plus the LRN.

Use this API when the merchant app has collected the customer identity credential through the approved UPI client library flow and the backend needs Newton to fetch Lite parameters from NPCI before the app completes the UPI Lite activation/top-up journey.

## Business Use Case

This API helps merchants:

- Fetch NPCI Lite keys for a customer bank account.
- Bind an NPCI LRN to the customer's Newton merchant-customer account context.
- Create or update Newton's UPI Lite account record for the merchant customer and device.
- Enforce the configured count of active UPI Lite accounts per merchant app when the new UPI Lite flow is enabled.
- Support normal Newton account references, account hashes, and the GPay ICICI migrated-account lookup path.
- Pass the CL version to NPCI where the integration needs CL-version-specific behavior.

## Integration Flow

1. Customer completes device binding and account discovery/linking through the existing Newton UPI integration.
2. Merchant app obtains the UPI Lite identity credential block from the approved client library.
3. Merchant backend chooses the customer account using either `accountReferenceId` or `bankAccountUniqueId`. For GPay ICICI migrated-account flows, send `accountReferenceId` plus `ifsc`.
4. Merchant backend sends the encrypted or signed S2S request to Newton with merchant headers and timestamp/signature data.
5. Newton decrypts/verifies the request envelope and resolves merchant, customer, merchant-customer, device, and account records.
6. Newton validates the customer's UPI Lite account count/state where configured.
7. Newton extracts `identitycred` from `credBlock`, combines it with the stored device fingerprint, app package name, customer mobile number, and CL encrypted credential data, and calls NPCI `ReqListKeys`.
8. On NPCI success, Newton stores or updates the LRN/UPI Lite record and returns `respListKeys`, `lrn`, and key rotation metadata.
9. Merchant backend decrypts the response and passes the Lite parameters to the app flow that completes activation/top-up.

Important identifiers:

- `merchantCustomerId`: Merchant's customer id. Also used by auth middleware to load Newton's merchant-customer and customer records.
- `accountReferenceId`: Newton account id for the customer account in standard flows. In GPay ICICI migrated flows it can be a migrated account reference instead of the Newton account id.
- `bankAccountUniqueId`: Account hash / bank account unique id used to resolve the merchant customer account.
- `upiRequestId`: Merchant-generated request id for this Lite params call. Newton uses it to derive the NPCI transaction id.
- `lrn`: Lite Reference Number returned by NPCI and persisted by Newton.

## Endpoint

```http
POST /api/{apiVersion}/merchants/npci/lite/account
```

Payloads use Newton's standard server-to-server `EncRequest` and `EncResponse` envelope. The examples in this guide show decrypted business payloads and decrypted business responses for readability.

### Headers, Auth, Encryption, and Signing

Use the S2S encryption/signing configuration shared during onboarding. The route accepts the shared `EncRequest` shapes: JWE encrypted body, JWS signed body, or plain JSON in environments where that is explicitly enabled. Production clients should use the onboarded encrypted/signed mode.

Recommended and expected headers:

| Header | Required | Description |
| --- | --- | --- |
| `Content-Type: application/json` | Yes | Request body is JSON, either an encrypted/signed envelope or the decrypted payload in non-production/test setups. |
| `x-merchant-id` | Yes | Merchant id used to load the merchant record. |
| `x-merchant-channel-id` | Yes | Merchant channel id used with `x-merchant-id`. |
| `x-sub-merchant-id` | Conditional | Required only when onboarded as a sub-merchant flow. |
| `x-sub-merchant-channel-id` | Conditional | Required only when onboarded as a sub-merchant flow. |
| `x-timestamp` | Yes | Request timestamp used by signature middleware. It is also validated as a timestamp unless a development/UAT checksum bypass applies. |
| `x-raw-body` | Yes | Exact raw request body used by signature verification. |
| `x-merchant-signature` | Required for unsigned/plain requests and for integrations configured to use this header | Signature over merchant id, channel id, optional sub-merchant ids, timestamp, and raw body. |
| `Authorization` | Conditional | Present when required by the onboarded envelope/signature mode. |
| `x-forwarded-for` | Conditional | Required when merchant configuration has `whitelistedIps`; the first IP in this header must be allowed. |
| `x-request-id` | No | Optional request correlation id. Newton generates one if omitted. |
| `x-session-id` | No | Optional session correlation id. Defaults to `x-request-id` when omitted. |

Encrypted request envelope shape:

```json
{
  "protected": "<jwe-protected-header>",
  "encryptedKey": "<encrypted-key>",
  "iv": "<initialization-vector>",
  "cipherText": "<encrypted-payload>",
  "tag": "<auth-tag>"
}
```

Signed request envelope shape:

```json
{
  "payload": "<base64url-encoded-json-payload>",
  "signature": "<jws-signature>",
  "protected": "<jws-protected-header>"
}
```

Decrypted error bodies may be returned inside the encrypted response envelope depending on deployment and request mode. The examples below show the underlying decrypted JSON.

## Request

### Required Minimum - Standard Account Reference

```json
{
  "merchantCustomerId": "CUST12345",
  "upiRequestId": "LITEKEYS000000000000000001",
  "accountReferenceId": "ACCREF1234567890",
  "credBlock": "{\"identitycred\":{\"subType\":\"IDENTITY\",\"data\":{\"code\":\"NPCI\",\"encryptedBase64String\":\"<encrypted-identity-credential>\",\"ki\":\"<key-index>\"},\"type\":\"DEVICE\"}}",
  "iat": "2026-07-02T10:15:30+05:30"
}
```

### Request With Bank Account Unique Id

Use this when your integration identifies the customer account by the account hash / bank account unique id mapped to the merchant customer account.

```json
{
  "merchantCustomerId": "CUST12345",
  "upiRequestId": "LITEKEYS000000000000000002",
  "bankAccountUniqueId": "BANKACCHASH1234567890",
  "credBlock": "{\"identitycred\":{\"subType\":\"IDENTITY\",\"data\":{\"code\":\"NPCI\",\"encryptedBase64String\":\"<encrypted-identity-credential>\",\"ki\":\"<key-index>\"},\"type\":\"DEVICE\"}}",
  "iat": "2026-07-02T10:16:30+05:30"
}
```

### Request With CL Version

Send `clVersion` when Newton/NPCI onboarding requires the Lite key request to include the client library version. Newton forwards it to NPCI as `Txn.clVersion`.

```json
{
  "merchantCustomerId": "CUST12345",
  "upiRequestId": "LITEKEYS000000000000000003",
  "accountReferenceId": "ACCREF1234567890",
  "clVersion": "2.0",
  "credBlock": "{\"identitycred\":{\"subType\":\"IDENTITY\",\"data\":{\"code\":\"NPCI\",\"encryptedBase64String\":\"<encrypted-identity-credential>\",\"ki\":\"<key-index>\",\"hmac\":\"<hmac-if-supplied>\"},\"type\":\"DEVICE\"}}",
  "iat": "2026-07-02T10:17:30+05:30"
}
```

### GPay ICICI Migrated Account Request

For the GPay ICICI path, `accountReferenceId` is mandatory. If it is not a Newton account id with the configured account-id prefix, Newton treats it as a migrated account reference and also requires `ifsc`.

```json
{
  "merchantCustomerId": "CUST12345",
  "upiRequestId": "LITEKEYS000000000000000004",
  "accountReferenceId": "MIGRATEDACC12345",
  "ifsc": "ICIC0000123",
  "credBlock": "{\"identitycred\":{\"subType\":\"IDENTITY\",\"data\":{\"code\":\"NPCI\",\"encryptedBase64String\":\"<encrypted-identity-credential>\",\"ki\":\"<key-index>\"},\"type\":\"DEVICE\"}}",
  "iat": "2026-07-02T10:18:30+05:30"
}
```

## Field Reference

| Field | Type | Required | Default / omitted behavior | Validation and rules | Description |
| --- | --- | --- | --- | --- | --- |
| `merchantCustomerId` | string | Yes | No default. | Should be 1 to 256 characters and match `^[a-zA-Z0-9+/=][a-zA-Z0-9._+/=-]*$`. Auth middleware uses it to fetch the merchant-customer and customer records. | Merchant's customer identifier. |
| `upiRequestId` | string | Yes | No default. | Should be 1 to 35 alphanumeric characters. Newton uses it to derive the NPCI transaction id. | Request id for this Lite params call. Reuse only for reconciliation of the same attempt. |
| `bankAccountUniqueId` | string | Conditional | No default. | When supplied, must be non-empty. Standard Newton lookup uses it to find the merchant customer account. | Account hash / bank account unique id. Send either this or `accountReferenceId` for normal Newton flows. |
| `accountReferenceId` | string | Conditional | No default. | When supplied, must be non-empty. For standard Newton flows, this is the account id. For GPay ICICI, it is mandatory and may be a migrated account reference. | Customer account reference. |
| `ifsc` | string | Conditional | No default. | When supplied, must be non-empty. Required for GPay ICICI migrated-account lookup when `accountReferenceId` is not the Newton account id format. | Account IFSC for migrated-account lookup. Newton sends stored/decrypted account IFSC to NPCI. |
| `clVersion` | string | No | Omitted from NPCI request when not supplied. | When supplied, must be non-empty. | Client library version forwarded to NPCI. |
| `credBlock` | stringified JSON | Yes | No default. | Must parse as JSON containing `identitycred`. If `identitycred` is missing or cannot decode into the expected credential type, processing fails with a bad request style response. | Credential block generated by the approved client library. Newton extracts `identitycred`. |
| `iat` | string | Required for signed/encrypted requests | No default. | For signed/encrypted request envelopes, middleware requires `iat` and validates it as a timestamp. Plain/unsigned payloads do not use this timestamp check, but production clients should still send it. | Issued-at timestamp in the decrypted payload. |

Important implementation note: the request type defines field-level validation rules for the formats above, but the current product route does not explicitly run the shared field-validation step. JSON parsing still requires all non-optional fields, auth middleware still validates `iat` for encrypted/signed requests, and product logic still enforces lookup and business rules. Clients should follow the validation contract above so the same payload remains compatible if stricter validation is enabled for this route.

### Account Selection Rules

| Scenario | Required fields | Runtime behavior |
| --- | --- | --- |
| Standard Newton account id | `accountReferenceId` | Newton fetches the active account by account id and customer id. |
| Account hash / bank account unique id | `bankAccountUniqueId` | Newton fetches the merchant customer account by account hash and merchant customer id, then fetches the linked active account. |
| Neither account id nor account hash | None | Fails with `BAD_REQUEST` message `bankAccountUniqueId or accountReferenceId is mandatory`, except VPA-based lookups in other code paths not used by this route. |
| GPay ICICI account id | `accountReferenceId` with account-id prefix | Newton resolves the merchant customer account, then fetches the active account by stored account id. |
| GPay ICICI migrated account | `accountReferenceId`, `ifsc` | Newton finds the account by migrated id, IFSC, and customer id, then verifies the merchant customer account is active. |

### `credBlock` Inner Shape

The top-level `credBlock` field is a string that contains JSON. For this API, Newton reads only `identitycred`.

```json
{
  "identitycred": {
    "subType": "IDENTITY",
    "data": {
      "code": "NPCI",
      "encryptedBase64String": "<encrypted-identity-credential>",
      "ki": "<key-index>",
      "hmac": "<optional-hmac>",
      "pid": "<optional-pid>",
      "skey": "<optional-skey>",
      "type": "<optional-data-type>"
    },
    "type": "DEVICE"
  }
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `identitycred.subType` | string | Yes | Credential subtype. Expected client-library value for this flow is `IDENTITY`. Newton forwards the credential to NPCI as `DEVICE` / `IDENTITY`. |
| `identitycred.type` | string | Yes | Credential type. Expected value is `DEVICE`. |
| `identitycred.data.code` | string | Yes | Credential code, usually `NPCI`. Forwarded to NPCI. |
| `identitycred.data.encryptedBase64String` | string | Yes | Encrypted identity credential from the client library. Newton combines it with stored device fingerprint, package name, and mobile number before calling NPCI. |
| `identitycred.data.ki` | string | Yes | Key index forwarded to NPCI. |
| `identitycred.data.hmac` | string | No | Optional HMAC from the client library. Parsed as part of the CL credential object but not separately used by this route's transformer. |
| `identitycred.data.pid` | string | No | Optional PID field from the client library. |
| `identitycred.data.skey` | string | No | Optional session key field from the client library. |
| `identitycred.data.type` | string | No | Optional nested credential data type. |

## Defaults and Omitted Field Behavior

- `bankAccountUniqueId`, `accountReferenceId`, and `ifsc` have no defaults. At least one supported account identifier is required for runtime account lookup.
- `clVersion` has no default. When omitted, Newton does not send `Txn.clVersion` to NPCI.
- `iat` has no default and is required by middleware for encrypted/signed envelopes.
- `credBlock` has no default. Newton does not synthesize the identity credential.
- `rotation` in the success response comes from runtime configuration `rotationPeriodClLiteParams`; the current environment default is configured as `29` if not overridden.

## Response

### Success Response

```json
{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "respListKeys": "<raw-npci-resp-list-keys-xml>",
    "lrn": "123456789012",
    "gatewayResponseMessage": "Get Lite Keys fetched successfully",
    "gatewayResponseCode": "00",
    "gatewayResponseStatus": "SUCCESS",
    "rotation": "29"
  }
}
```

### Response Envelope Notes

The route response type is `EncResponse GetLiteParamsS2SResponse`. Depending on the request mode and deployment, the HTTP response may be encrypted/signed using the standard Newton envelope. After decryption, the business response has the shape shown above.

NPCI business failures can still be returned with a top-level `status` of `FAILURE`, even though HTTP status may be 200 in some layers. Always use the decrypted JSON fields, not HTTP status alone.

### Field Reference

| Field | Type | Description |
| --- | --- | --- |
| `status` | string | Newton API status. `SUCCESS` when NPCI returned Lite keys and Newton mapped them successfully. |
| `responseCode` | string | Newton response code. Success is `SUCCESS`. NPCI business errors use `BAD_RESPONSE_FROM_NPCI`; timeouts use `SERVICE_UNAVAILABLE`; validation/auth failures use their shared codes. |
| `responseMessage` | string | Human-readable Newton response message. |
| `payload` | object | Present on success and on some NPCI business failures. Omitted on timeout/auth/config/internal failures. |
| `payload.respListKeys` | string | Raw NPCI `RespListKeys` XML returned by NPCI. Present on success. |
| `payload.lrn` | string | Lite Reference Number extracted from NPCI account details. Present on success. |
| `payload.gatewayResponseMessage` | string | Gateway/NPCI-facing message. Success is `Get Lite Keys fetched successfully`; NPCI failures use the mapped error detail when available. |
| `payload.gatewayResponseCode` | string | Gateway/NPCI response code. Success is `00`. |
| `payload.gatewayResponseStatus` | string | `SUCCESS` or `FAILURE` for the downstream NPCI result. |
| `payload.rotation` | string | Key rotation period from configuration. Present on success; omitted on NPCI business failure. |

## Failure Scenarios and Client Handling

Failure bodies are shown as decrypted JSON. In encrypted/signed deployments, the same business body may be wrapped in `EncResponse`.

| Scenario | Example decrypted response | Client handling |
| --- | --- | --- |
| Missing required JSON field such as `merchantCustomerId`, `upiRequestId`, or `credBlock` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"Error in $: key \"merchantCustomerId\" not found"}` | Fix the request. Do not retry unchanged. Exact parse error text can vary by JSON parser/envelope layer. |
| Empty or malformed field if the shared validator is enabled for this route | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"LengthValidation \"accountReferenceId field is empty\""}` | Fix the field. Use the validation rules in this guide. |
| Signed/encrypted payload missing `iat` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"IAT is empty"}` | Add a valid `iat` timestamp and retry with a fresh signature/envelope. |
| Invalid or expired `iat` or `x-timestamp` | `{"status":"FAILURE","responseCode":"REQUEST_EXPIRED","responseMessage":"REQUEST_EXPIRED"}` | Regenerate payload, timestamps, and signature. Do not replay old requests. |
| Missing merchant headers, raw body, or merchant signature | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` | Send `x-merchant-id`, `x-merchant-channel-id`, `x-timestamp`, `x-raw-body`, and the configured signature/envelope fields. |
| JWS/JWE verification or decryption fails | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` | Check key id, public/private keys, JWE/JWS construction, and whether the exact raw body was signed. |
| IP restriction fails | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` | Send traffic from a whitelisted IP and ensure `x-forwarded-for` contains that IP as the first value. |
| API blocked or not allowed for merchant | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"API NOT ENABLED"}` | Ask Newton to enable `getLiteParamsS2S` / Lite params access for the merchant or sub-merchant. Do not retry until configuration is fixed. |
| Merchant, merchant-customer, customer, device, or account record not found | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` or `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"bankAccountUniqueId or accountReferenceId is mandatory"}` | Verify onboarding state, customer registration, device binding, and account identifiers. Missing identifiers are client-fixable; missing stored records require reconciliation or re-registration. |
| GPay ICICI request missing `accountReferenceId` or required migrated-account `ifsc` | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` | Send `accountReferenceId`; when using a migrated id, also send `ifsc`. |
| UPI Lite account limit exceeded | `{"status":"FAILURE","responseCode":"JPLL","responseMessage":"UPI Lite A/C limit 1 is reached for the Merchant App"}` | Do not retry unchanged. Ask the customer to use an existing Lite account or deactivate another Lite account as per product flow. |
| `credBlock` is not valid JSON or does not contain decodable `identitycred` | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"getLiteParamsRoute-identityCredMaybe"}` | Regenerate the identity credential in the app and send the full `identitycred` JSON string. |
| Stored device fingerprint, package name, mobile number, account IFSC/type/number, account hash, or NPCI LRN/raw XML missing unexpectedly | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` | Treat as non-retryable until Newton support checks customer/device/account state. Include `merchantCustomerId` and `upiRequestId` in the escalation. |
| NPCI returns a business failure response | `{"status":"FAILURE","responseCode":"BAD_RESPONSE_FROM_NPCI","responseMessage":"Invalid response from NPCI","payload":{"gatewayResponseMessage":"INVALID_KEY- Keys passed in ARQC is wrong","gatewayResponseCode":"IK","gatewayResponseStatus":"FAILURE"}}` | Treat as a completed downstream decline. Show a mapped customer/action message where applicable. Retry only after the customer regenerates credentials or changes the failing input. |
| NPCI immediate failure with error details | `{"status":"FAILURE","responseCode":"BAD_RESPONSE_FROM_NPCI","responseMessage":"Invalid response from NPCI","payload":{"gatewayResponseMessage":"INVALID_KEY- Keys passed in ARQC is wrong","gatewayResponseCode":"IK","gatewayResponseStatus":"FAILURE"}}` | Use `gatewayResponseCode` and `gatewayResponseMessage` for reconciliation. Retry only if the code is known to be transient for your integration. |
| NPCI timeout | `{"status":"FAILURE","responseCode":"SERVICE_UNAVAILABLE","responseMessage":"UPI service is not reachable at the moment"}` | Treat as ambiguous. Do not assume Lite params were not created. Retry with a new `upiRequestId` only after checking the customer Lite/account state or following Newton's reconciliation guidance. |
| NPCI decode failure or Redis correlation entry missing | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` | Treat as technical failure. Retry later with a new `upiRequestId` if the customer flow can safely restart; otherwise escalate. |
| Unexpected internal error | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` | Retry only if your integration policy allows technical retries. Escalate repeated failures with `x-request-id`, `merchantCustomerId`, and `upiRequestId`. |

## Retry and Idempotency Guidance

`upiRequestId` is the request identifier used to derive the NPCI transaction id. The API does not expose a separate idempotency key and does not implement a replay-safe idempotent response lookup in this route.

Recommended client behavior:

- Generate a unique `upiRequestId` for each Lite params attempt.
- Do not reuse a failed request unchanged unless Newton support explicitly asks you to replay it.
- For validation, auth, merchant config, IP restriction, account lookup, or Lite account limit errors, fix the root cause before retrying.
- For NPCI business failures, treat the result as terminal for that credential/account attempt unless the customer regenerates credentials or changes account context.
- For NPCI timeout or internal technical failure, treat the result as ambiguous. Check current Lite account state through your normal customer/account flow before starting a new Lite activation attempt.
- If the customer retries from the app, create a fresh `credBlock`, `iat`, signature/envelope, and `upiRequestId`.
