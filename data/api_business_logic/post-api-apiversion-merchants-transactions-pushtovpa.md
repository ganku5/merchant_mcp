# Push To VPA API Integration Guide

Source endpoint: `POST /api/{apiVersion}/merchants/transactions/pushToVpa`

## Overview

Push To VPA is a server-to-server payout API. It lets a merchant initiate an outward UPI payment from the merchant's configured payout/refund VPA to a beneficiary identified by either a VPA or a UPI number.

Newton creates a payout transaction record, attempts the configured payout rail, and returns the current gateway status. The response can be `SUCCESS`, `PENDING`, `DEEMED`, or `FAILURE` at the payout layer, so merchants should store the returned identifiers and use Push To VPA Status or callbacks for final reconciliation when the first response is not terminal.

Payloads use the standard Newton server-to-server request and response envelope. The examples below show decrypted business payloads for readability.

## Business Use Case

Use this API when the merchant backend needs to push money to a customer's UPI destination, for example:

- Customer payout to a known VPA.
- Customer payout to a 10-digit UPI number, where Newton resolves the UPI number to the mapped VPA before initiating the payout.
- Payouts funded from the merchant's configured payout/refund VPA.
- PPI or YESBIZ payout flows where the merchant has been enabled for the corresponding payout rail.

Important identifiers:

- `merchantRequestId`: Merchant-generated idempotency key for this payout. Use a new value for each new payout attempt.
- `upiRequestId`: UPI transaction id. If omitted, Newton generates one and returns it as `payload.gatewayTransactionId`.
- `gatewayReferenceId`: Customer reference number generated by Newton for NPCI outward/PPI flows when available.
- `gatewayTransactionId`: The UPI transaction id stored by Newton. Use this with `merchantRequestId` for reconciliation and status checks.

## Integration Flow

1. Merchant creates a payout request in its own system.
2. Merchant calls `pushToVpa` with amount, payout VPA, one payee identifier, and a unique `merchantRequestId`.
3. Newton authenticates the merchant request, validates the payload, and checks merchant API access/IP restrictions.
4. Newton resolves `upiNumber` to a VPA when `customerVpa` is not supplied.
5. Newton locates the merchant payout/refund account for `merchantVpa`.
6. Newton creates a payout transaction. If `upiRequestId` was omitted, Newton generates it.
7. Newton initiates payout processing on the configured rail:
   - YESBIZ: debit from virtual account, then push to VPA through NPCI.
   - PPI-enabled pre-approved flow: push to VPA through NPCI/PPI flow.
   - Other PSP modes: m-prepay payout flow.
8. Newton forks the `CUSTOMER_PUSH_TO_VPA` merchant callback when configured.
9. Merchant stores the response and polls `pushToVpa/status` or consumes callbacks for final status when needed.


## Authentication, Signing, and Encryption

The route accepts the standard Newton S2S request envelope:

- Plain business JSON (`UnSignedPayload` in code) with merchant signature headers.
- JWS signed payload.
- JWS plus JWE encrypted payload.

For plain business JSON, Newton verifies `x-merchant-signature` over:

```text
x-merchant-id + x-merchant-channel-id + x-sub-merchant-id + x-sub-merchant-channel-id + x-timestamp + raw request body
```

Sub-merchant header parts are empty when not supplied. The signature strategy and API key are merchant-configured during onboarding.

For JWS/JWE requests, `iat` in the decrypted business payload is required and must be a valid 13-digit epoch-millisecond timestamp within the allowed clock skew. Responses follow the merchant's configured response strategy:

- JWS: signed response body.
- JWS_AND_JWE: signed and encrypted response body.
- Legacy/plain strategy: plain JSON body with `X-Response-Signature`.

All decrypted examples below show the business payload inside the transport envelope.

### Field Reference

| Field | Type | Required | Default / omitted behavior | Description |
| --- | --- | --- | --- | --- |
| `merchantRequestId` | string | Yes | No default. | Merchant-generated unique payout reference and idempotency key. Max 35 characters. Allowed characters: letters, numbers, hyphen, dot, underscore. |
| `customerVpa` | string | Conditional | If omitted, `upiNumber` must be supplied. When `upiNumber` is supplied, Newton resolves it to a VPA and stores the resolved VPA as the payee VPA. | Beneficiary/customer VPA. Exactly one of `customerVpa` or `upiNumber` must be present. |
| `upiNumber` | string | Conditional | If omitted, `customerVpa` must be supplied. | 10-digit beneficiary UPI number. Newton resolves `<upiNumber>@mapper.npci` before payout. Exactly one of `customerVpa` or `upiNumber` must be present. |
| `amount` | string | Yes | No default. | Payout amount in two-decimal format, for example `100.00`. Must be greater than `0.00`. |
| `merchantVpa` | string | Yes | No default. | Merchant payout/refund VPA to debit. Must match a configured refund merchant/account for the authenticated merchant. |
| `remarks` | string | Yes | No default. | Payout note. Must be 1 to 255 characters and match the allowed remarks format. |
| `upiRequestId` | string | No | Newton generates a transaction id when omitted. | Merchant-supplied UPI transaction id. Max 35 characters; letters and numbers only. If supplied, it participates in duplicate detection. |
| `transactionReference` | string | No | If omitted, Newton uses `merchantRequestId` as the transaction reference in NPCI payout metadata. | Optional transaction reference (`tr`) sent in payout metadata for outward NPCI flows. 1 to 35 alphanumeric characters. |
| `mcc` | string | No | Not stored directly by this route when omitted. | Optional merchant category code. Must be exactly 4 digits when supplied. |
| `iat` | string | Conditional | Required for signed/encrypted request envelopes. Ignored for plain unsigned business JSON. | Issued-at timestamp in epoch milliseconds used by S2S envelope validation. |
| `isPreApproved` | boolean | No | Omitted or `false` uses the normal PSP path. `true` activates the PPI push-to-VPA path only when the merchant/environment feature flag is enabled. | Indicates a pre-approved/PPI payout use case. |
| `udfParameters` | string | No | Omitted from response and callback when not supplied. | JSON-object string for merchant-defined metadata. Must parse as a JSON object string and must not contain restricted characters such as `/`, `$`, `-`, `*`, `!`, `%`, `~`, or backtick. Echoed in the API response and merchant callback. |

### Validation Rules

- `customerVpa` and `upiNumber` are mutually exclusive.
- One of `customerVpa` or `upiNumber` is mandatory.
- `customerVpa` and `merchantVpa` must be 3 to 255 characters and match `local-part@handle` format using letters, numbers, dot, and hyphen.
- `upiNumber` must be exactly 10 digits.
- `amount` must match `^[0-9]+\.[0-9][0-9]$` and must be greater than `0.00`.
- `merchantRequestId` must be 1 to 35 characters and contain only letters, numbers, hyphen, dot, or underscore.
- `upiRequestId` must be 1 to 35 alphanumeric characters when supplied.
- `transactionReference` must be 1 to 35 alphanumeric characters when supplied.
- `mcc` must be exactly 4 digits when supplied.
- `remarks` must be 1 to 255 characters, start with an alphanumeric character after optional leading spaces, and contain only letters, numbers, spaces, and hyphen.
- `udfParameters` must be a stringified JSON object, for example `"{\"key\":\"value\"}"`.
- For signed/encrypted envelopes, `iat` must be present and valid. Separately, `x-timestamp` must be valid for all non-development signed-header flows.

### Defaults and Omitted Field Behavior

- `upiRequestId`: generated by Newton when omitted and returned as `payload.gatewayTransactionId`.
- `transactionReference`: omitted behavior is to use `merchantRequestId` as the `tr` value in NPCI outward metadata.
- `customerVpa`: when `upiNumber` is supplied, Newton resolves the UPI number and lowercases the resolved VPA before storing it.
- `merchantVpa`: lowercased before encrypted storage and payout processing, but the request must still supply a configured merchant payout VPA.
- `isPreApproved`: omitted behaves as `false`.
- Optional fields not listed above have no default and are not returned unless produced by downstream payout/status processing.

## Duplicate and Idempotency Behavior

Before creating a payout, Newton checks whether a refund/payout transaction already exists for the authenticated merchant using `merchantRequestId` and the optional `upiRequestId`.

If a matching transaction exists, the API rejects the request with `DUPLICATE_REQUEST`. It does not return the original payout response from this endpoint. Treat `merchantRequestId` as a single-use idempotency key:

- Retry the same request only when you did not receive any HTTP response or could not decrypt/read the response.
- If a retry returns `DUPLICATE_REQUEST`, call Push To VPA Status with the same `merchantRequestId` to reconcile the existing payout.
- Do not reuse `merchantRequestId` for a new payout, even with a different amount or payee.
- If you supply `upiRequestId`, do not reuse it across payouts for the same merchant.

## Payout Behavior

Newton stores this request as a self-initiated payout transaction with type `PAY`. The payee is the customer VPA or the VPA resolved from UPI number. The payer is the refund/payout merchant account configured for `merchantVpa`.

Rail selection:

- If the PSP name is `YESBIZ`, Newton creates a CBS debit transaction with YESPAYHUB type, debits the virtual account, and then initiates push-to-VPA through NPCI.
- If `isPreApproved` is `true` and the merchant feature `isPushToVpaActivatedForPPI` is enabled, Newton uses the PPI push-to-VPA path.
- Otherwise, Newton initiates the m-prepay payout path.

For NPCI/PPI/YESBIZ outward flows, Newton may mark the payout `PENDING` or `DEEMED` while the downstream system is still processing. Use status checks/callbacks for the final outcome.

When merchant configuration contains `pushToVpaTimeLimit`, status/retry processing can mark an old pending payout as `FAILURE` with a payout error code if the configured time limit has expired.

## Failure Scenarios

Failure responses use the same transport strategy as other S2S responses when the request reaches the application flow. Authentication failures may be returned as plain error JSON depending on where the request fails. After decryption or parsing, Newton error bodies use this shape:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "Both CustomerVpa/UpiNumber cannot be present"
}
```

Some internal error bodies also include `"payload": null`.

### Validation Failures

Missing required JSON fields can fail JSON parsing before business validation. Business validation failures use `BAD_REQUEST` with the validation message. Examples:

### Duplicate Request

Returned when the merchant already has a payout/refund transaction matching the submitted `merchantRequestId` and optional `upiRequestId`.

```json
{
  "status": "FAILURE",
  "responseCode": "DUPLICATE_REQUEST",
  "responseMessage": "DUPLICATE_REQUEST"
}
```

Client handling: do not create a new payout with the same reference. Call Push To VPA Status to reconcile.

### Authentication, Signature, and Encryption Failures

Missing merchant id/channel id, missing raw body, missing signature for plain payloads, signature mismatch, invalid request timestamp, invalid `iat` for signed/encrypted payloads, and IP whitelist failures are rejected before payout processing.

Common unauthorized response:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "UNAUTHORIZED"
}
```

API blocked or not allowed for the merchant:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "API NOT ENABLED"
}
```

Encryption/decryption/signing failures in JWS/JWE processing may surface as:

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR"
}
```

### Merchant or Account Configuration Failures

The API requires:

- A valid merchant for `x-merchant-id` and `x-merchant-channel-id`.
- API access for `pushToVpa`.
- A configured refund/payout merchant account for `merchantVpa`.
- IP whitelist match when `whitelistedIps` is configured.
- PPI feature flag when using `isPreApproved: true` for PPI behavior.

Depending on the lookup layer, failures can appear as `UNAUTHORIZED`, `REQUEST_NOT_FOUND`, or `INTERNAL_SERVER_ERROR`. Examples:

```json
{
  "status": "FAILURE",
  "responseCode": "REQUEST_NOT_FOUND",
  "responseMessage": "REQUEST_NOT_FOUND"
}
```

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR"
}
```

### UPI Number Resolution Failures

When `upiNumber` is supplied, Newton resolves it before payout.

Invalid or unresolved UPI number:

```json
{
  "status": "FAILURE",
  "responseCode": "INVALID_DATA",
  "responseMessage": "Invalid UPI Number"
}
```

Mapper timeout or unavailable mapper response:

```json
{
  "status": "FAILURE",
  "responseCode": "GATEWAY_TIMEOUT",
  "responseMessage": "Mapper resolution timeout. Please try again."
}
```

### Downstream Payout Failures

If the payout rail returns a terminal failure but processing completes, the API can still return top-level `SUCCESS` with `payload.gatewayResponseStatus = "FAILURE"` and gateway code/message populated from the downstream response.

Example:

```json
{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "customerVpa": "customer@bank",
    "merchantId": "MERCHANT123",
    "merchantChannelId": "CHANNEL123",
    "merchantRequestId": "PAYOUT12348",
    "transactionAmount": "100.00",
    "gatewayReferenceId": "123456789014",
    "gatewayTransactionId": "NEWTONUPI123458",
    "gatewayResponseCode": "U30",
    "gatewayResponseMessage": "Debit failed",
    "gatewayResponseStatus": "FAILURE"
  }
}
```

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR"
}
```

## Retry and Client Handling

- Store `merchantRequestId`, `gatewayTransactionId`, `gatewayReferenceId`, `gatewayResponseStatus`, and gateway code/message for every readable response.
- Treat top-level `status = "SUCCESS"` as "request accepted/processed by Newton"; use `payload.gatewayResponseStatus` for payout state.
- For `SUCCESS` payout status, mark the payout successful after your normal reconciliation/callback checks.
- For `PENDING` or `DEEMED`, do not retry with a new `merchantRequestId`. Poll `POST /api/{apiVersion}/merchants/transactions/pushToVpa/status` or wait for `CUSTOMER_PUSH_TO_VPA` callback.
- For `FAILURE` payout status, treat the payout as failed unless your Newton integration team advises otherwise for a specific gateway code.
- For network timeout/no HTTP response, retry once with the same payload and same `merchantRequestId`. If the retry returns `DUPLICATE_REQUEST`, call status.
- For validation failures, fix the payload and submit a new `merchantRequestId` only if the original payout was not created.
- For `UNAUTHORIZED` or `API NOT ENABLED`, do not retry automatically; fix credentials, signature, headers, IP whitelist, or merchant API configuration.
- For `INTERNAL_SERVER_ERROR` after a request may have reached Newton, reconcile with status before creating a new payout.
