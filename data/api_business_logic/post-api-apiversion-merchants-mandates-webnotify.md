# Web Notify API Integration Guide

Source endpoint: `POST /api/{apiVersion}/merchants/mandates/webNotify`

## Overview

Web Notify is a server-to-server API used to notify the payer's UPI app before a mandate debit is executed.

The merchant calls this API for an upcoming mandate execution cycle. Newton validates the mandate, creates or reuses the mandate notification record for the supplied `merchantRequestId`, sends a `ReqValCust` notification request to NPCI/gateway, and returns the current notification status mapped into merchant-facing gateway fields.

Use this API when the merchant owns mandate execution scheduling and needs Newton to send the pre-debit mandate notification before executing or reconciling that cycle.

## Business Use Case

Use Web Notify when the merchant backend needs to:

- Notify a payer before a scheduled UPI mandate debit.
- Create a mandate notification cycle for an existing mandate.
- Reuse the same notification request id safely for retries after transient failures.
- Supply a merchant-generated UPI transaction id for reconciliation when required.
- Support mandate interoperability flows where the mandate may not already exist in Newton and the request must carry payer and mandate context.
- Optionally ask Newton to perform asynchronous status follow-up through Process Tracker when NPCI accepts the notification but the final status is pending.

Important identifiers:

- `umn`: UPI mandate number.
- `merchantRequestId`: Merchant idempotency key for this notification cycle. Use a new value for each cycle.
- `originalMerchantRequestId`: Merchant request id used when the mandate was created. Required for `x-api-version > 1`.
- `orgMandateId`: Mandate UPI request id. Required for interoperability flows where Newton does not find the mandate by UMN/original merchant request id.
- `upiRequestId`: Optional merchant-supplied UPI transaction id for this notification attempt. If omitted, Newton generates one internally, but it is not echoed in the S2S response.
- `seqNumber`: Mandate sequence number. Normally generated by Newton for stored mandates; required for interoperability flows and for merchants configured with request-body sequence validation.

## Integration Flow

1. Merchant creates or ports a mandate and stores `umn`, `originalMerchantRequestId`, `orgMandateId`, validity, recurrence, amount rule, and amount.
2. Before a debit cycle, merchant chooses a unique `merchantRequestId` for the notification cycle and decides the `mandateExecutionTimestamp`.
3. Merchant calls `webNotify` with the mandate identifiers, amount, execution timestamp, optional UPI request id, optional retry flag, and optional metadata.
4. Newton decrypts/parses the envelope, verifies merchant signature/auth headers, checks API allow/block config, checks IP restrictions if configured, validates the request body, and enforces the `x-api-version` rule for `originalMerchantRequestId`.
5. Newton loads the merchant/sub-merchant context, finds the mandate by `originalMerchantRequestId`, `umn`, merchant id, and PAYEE role, or switches to interoperability validation when the mandate is not stored and the purpose is an interoperability purpose.
6. Newton validates mandate status, execution timestamp window, validity period, amount rule, recurrence date, duplicate notification state, and sequence number.
7. Newton creates or updates the mandate notification and notification attempt, calls NPCI/gateway `ReqValCust`, and returns the mapped notification status.
8. Merchant stores `gatewayResponseStatus`, `gatewayResponseCode`, `gatewayTransactionId`, `seqNumber`, and `orgMandateId` for execution and reconciliation.

## Endpoint

```http
POST /api/{apiVersion}/merchants/mandates/webNotify
```

Payloads use the standard Newton server-to-server encrypted/signed request and response envelope. Examples below show decrypted business payloads for readability.

## Headers, Auth, Encryption, and Signing

| Header | Required | Description |
| --- | --- | --- |
| `Content-Type` | Yes | Send `application/json`. |
| `x-api-version` | Yes | API version shared during onboarding. For `x-api-version > 1`, the decrypted request must include `originalMerchantRequestId`. |
| `x-merchant-id` | Yes | Merchant id used to identify and authorize the merchant. |
| `x-merchant-channel-id` | Yes | Merchant channel id used with `x-merchant-id`. |
| `x-timestamp` | Yes | Timestamp used by merchant signature and replay validation. |
| `x-merchant-signature` | Conditional | Required for unsigned/plain payload integrations. The signature is calculated over merchant ids, optional sub-merchant ids, timestamp, and raw body using the merchant signature strategy. |
| `x-forwarded-for` | Conditional | Required when the merchant has `whitelistedIps` configured. Newton validates the first IP in the comma-separated header. |
| `x-request-id` | No | Client-supplied request id. Newton generates one when omitted and returns it in response headers. |
| `x-session-id` | No | Client-supplied session id. Defaults to `x-request-id` when omitted. |
| `x-sub-merchant-id` | Conditional | Required only for onboarded sub-merchant flows where the parent merchant sends sub-merchant context. |
| `x-sub-merchant-channel-id` | Conditional | Required with `x-sub-merchant-id` for sub-merchant flows. |

Envelope expectations:

- `EncRequest` accepts encrypted JWE, signed JWS, or unsigned payload shapes at the type level.
- S2S merchant integrations normally use the encrypted/signed envelope configured during onboarding.
- For encrypted or signed payloads, the decrypted/signed business payload must include `iat`; Newton validates it as a timestamp before product logic.
- For successful responses, Newton returns either an encrypted JWE response, signed JWS response, or unsigned response plus response signature, based on the merchant response signature strategy.
- Error responses may be returned before response encryption is possible, especially for malformed encrypted payloads, failed decryption, failed signature verification, missing headers, API-disabled checks, IP restriction failures, or timestamp failures.

## Request

### Standard Mandate Notification

Use this when Newton already has the mandate record. This is the common merchant-facing flow.

```json
{
  "umn": "12345678901234567890123456789012@upi",
  "amount": "100.00",
  "mandateExecutionTimestamp": "2026-07-04T10:00:00+05:30",
  "merchantRequestId": "NOTIFY000123",
  "originalMerchantRequestId": "MANDATE000123",
  "upiRequestId": "NOTIFYTXN000123",
  "remarks": "July subscription debit",
  "retryEnabled": "true",
  "udfParameters": "{\"cycleId\":\"JUL2026\",\"invoiceId\":\"INV8821\"}",
  "iat": "2026-07-02T10:15:30+05:30"
}
```

### Synchronous Notification

By default, Newton treats `makeAsync` as `true` and sends the NPCI notification on the asynchronous path. Send `makeAsync: "false"` only when Newton has enabled the synchronous callback path for your integration.

```json
{
  "umn": "12345678901234567890123456789012@upi",
  "amount": "100.00",
  "mandateExecutionTimestamp": "2026-07-04T10:00:00+05:30",
  "merchantRequestId": "NOTIFY000124",
  "originalMerchantRequestId": "MANDATE000123",
  "upiRequestId": "NOTIFYTXN000124",
  "makeAsync": "false",
  "remarks": "July subscription debit",
  "iat": "2026-07-02T10:16:30+05:30"
}
```

```json
  "initiationMode": "11",
  "subMerchantDetails": {
    "name": "Example Store",
    "mcc": "5411",
    "brandName": "EXAMPLESTORE",
    "legalName": "EXAMPLESTOREPRIVATE",

```

### Process Tracker Retry Metadata

`executeCycleDetails` is primarily written by Newton's Process Tracker retry flow. Merchants should not send `initiatedByProcessTracker: true` unless Newton has explicitly asked them to do so, because that mode expects a previous notification to exist and be in a retryable state.

```json
{
  "umn": "12345678901234567890123456789012@upi",
  "amount": "100.00",
  "mandateExecutionTimestamp": "2026-07-04T10:00:00+05:30",
  "merchantRequestId": "NOTIFY000123",
  "originalMerchantRequestId": "MANDATE000123",
  "upiRequestId": "NOTIFYTXN000123R",
  "executeCycleDetails": {
    "initiatedByProcessTracker": true,
    "mutualFundIds": [
      "MFORDER001",
      "MFORDER002"
    ]
  },
  "iat": "2026-07-02T10:18:30+05:30"
}
```

## Field Reference

| Field | Type | Required | Validation | Default / omitted behavior | Description |
| --- | --- | --- | --- | --- | --- |
| `umn` | string | Yes | Length 34 to 70. Must match `.{32}@.+`. | No default. | UPI mandate number. Used with `originalMerchantRequestId` and merchant id to find the PAYEE mandate. |
| `amount` | string | Yes | Must match `^[0-9]+\.[0-9][0-9]$` and be greater than `0.0`. | No default. | Amount to be notified for the cycle. For stored mandates, must satisfy the mandate amount rule: exact amount for `EXACT`, or not greater than mandate amount for `MAX`. |
| `mandateExecutionTimestamp` | string | Yes | Must parse as a Newton timestamp. Business validation also checks the configured notification lead-time window. | No default. | Planned mandate execution timestamp. Must be within mandate validity and recurrence rules. |
| `merchantRequestId` | string | Yes | Length 1 to 35. Allowed pattern: letters, numbers, hyphen, dot, underscore; must contain at least one letter or number. | No default. | Merchant-generated idempotency key for this notification cycle. Use a different value for each mandate execution cycle. |
| `originalMerchantRequestId` | string | Conditional | Same validation as `merchantRequestId`. | Required when `x-api-version > 1`. Optional for older API versions, but recommended. | Merchant request id used when the mandate was created. Used to locate the stored mandate. |
| `iat` | string | Conditional | Valid timestamp according to Newton timestamp validation. | Required for JWE/JWS payloads. Ignored for unsigned payload validation. | Issued-at timestamp used by request auth/replay checks. |
| `remarks` | string | No | Standard remarks validation. | Defaults to `Notification for Execution` when omitted. | Note stored on the notification and sent in the NPCI `ReqValCust` transaction note. |
| `retryEnabled` | string | No | Parsed as a boolean-like string by business logic. Use `true` or `false`. | Omitted behaves as `false` when the notification is inserted. | When true and NPCI accepts the async notification, Newton schedules notification status follow-up through Process Tracker. |
| `udfParameters` | string | No | Must be a JSON object encoded as a string. The text must not contain `/`, `$`, `-`, `*`, `!`, `%`, `~`, or backtick. | Omitted from the response when omitted. | Merchant-defined metadata stored with the notification and echoed in a successful response. |
| `upiRequestId` | string | No | Length 1 to 35. Letters and numbers only. | If omitted, Newton generates the notification attempt UPI request id internally. The generated id is not returned as `gatewayTransactionId`. | Merchant-supplied UPI transaction id for this notification attempt. Send this when you need response-level reconciliation. |
| `executeCycleDetails` | object | No | See nested table. | No default. | Internal/process-tracker metadata for retrying a web execute cycle notification. |
| `makeAsync` | string | No | Must be `true` or `false`, case-insensitive. | Omitted behaves as `true`. | Controls async vs sync NPCI notification call path. Use only as configured by Newton. |
| `orgMandateId` | string | Conditional | Same validation as `upiRequestId`. | Required when Newton does not have the mandate locally and the purpose is an interoperability purpose. | Mandate UPI request id. |
| `purpose` | string | Conditional | Exactly 2 characters. Uppercase letters and digits only. | For stored mandates, Newton uses the mandate's stored purpose when omitted. | UPI purpose code. Must match the stored mandate purpose when both are present. Required for interoperability when the mandate is not stored. |
| `payerName` | string | Conditional | No request-level validator in this type. | Required for interoperability when the mandate is not stored. | Payer display name used to build the notification request. |
| `payerVpa` | string | Conditional | VPA length 3 to 255 and pattern `^[a-zA-Z0-9.-]{1,}@[a-zA-Z0-9.-]{1,}$`. | Required for interoperability when the mandate is not stored. | Payer VPA. |
| `payeeVpa` | string | Conditional | Same VPA validation as payer VPA. | Required only when dynamic VPA is enabled for the merchant. Rejected when dynamic VPA is not enabled. | Payee VPA for dynamic VPA/interoperability flows. |
| `subMerchantDetails` | object | Conditional | See nested table. | Required when dynamic VPA is enabled and confirm-VPA-resolution is configured. | Sub-merchant context used for dynamic VPA or aggregator flows. |
| `seqNumber` | string | Conditional | Must parse as an integer greater than or equal to `0` at request validation. Business validation requires the effective value to be greater than `0`. | For stored mandates, Newton generates the sequence number unless merchant config `seqNumberFromRequestBody` is enabled or the purpose is interoperability. | Mandate notification sequence number. Required for interoperability and request-sequence-number merchants. |
| `initiationMode` | string | Conditional | No request-level validator in this type. | Required for interoperability when the mandate is not stored. | UPI initiation mode sent in the notification request. |

### Conditional Rules

- `originalMerchantRequestId` is mandatory when `x-api-version > 1`; omission returns `INVALID_DATA` with message `originalMerchantRequestId not found`.
- For stored mandates, Newton looks up a PAYEE mandate by `originalMerchantRequestId`, `umn`, and merchant id. If no mandate is found and `purpose` is not an interoperability purpose, the request fails with `Mandate not present`.
- If both request `purpose` and stored mandate purpose are present, they must match.
- For interoperability purpose flows, if a mandate is found, `seqNumber` is mandatory. If no mandate is found, `payerVpa`, `payerName`, `initiationMode`, `orgMandateId`, and `seqNumber` are mandatory.
- For dynamic VPA flows, `payeeVpa` is required. If dynamic VPA is not enabled, sending `payeeVpa` is rejected.
- If dynamic VPA and confirm-VPA-resolution are both enabled, `subMerchantDetails` is required.
- If `subMerchantDetails.accountNumber`, `subMerchantDetails.ifsc`, or `subMerchantDetails.accountType` is supplied, all three must be supplied together.
- `mandateExecutionTimestamp` must be within the configured notification window, within mandate validity, and valid for the mandate recurrence schedule.
- For stored mandates, status must allow notification. `PENDING`, `COMPLETED`, `DECLINED`, `EXPIRED`, revoked states, `FAILURE`, `TIMED_OUT`, and `DORMANT` are rejected.
- For non-`ASPRESENTED` mandates, Newton rejects a new notification if another valid notification already exists for the same sequence number.
- If `executeCycleDetails.initiatedByProcessTracker` is `true`, a previous notification must exist for the same `merchantRequestId`, and it must be in `FAILURE_RETRY`.

## Success Response

For a successful API call, the top-level `status`, `responseCode`, and `responseMessage` describe whether the request was accepted and processed by Newton. The notification business state is in `payload.gatewayResponseStatus`, `payload.gatewayResponseCode`, and `payload.gatewayResponseMessage`.

### Pending Notification

NPCI/gateway accepted the notification request or Newton is waiting for the final async result.

```json
{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "merchantId": "MERCHANT001",
    "merchantChannelId": "APP",
    "merchantRequestId": "NOTIFY000123",
    "originalMerchantRequestId": "MANDATE000123",
    "umn": "12345678901234567890123456789012@upi",
    "nextExecution": "2026-07-04T10:00:00+05:30",
    "amount": "100.00",
    "remarks": "July subscription debit",
    "orgMandateId": "MANDATEUPIREQ000001",
    "gatewayResponseCode": "01",
    "gatewayResponseMessage": "Mandate notification pending",
    "gatewayResponseStatus": "PENDING",
    "gatewayTransactionId": "NOTIFYTXN000123",
    "seqNumber": "3"
  },
  "udfParameters": "{\"cycleId\":\"JUL2026\",\"invoiceId\":\"INV8821\"}"
}
```

Client handling:

- Treat `gatewayResponseStatus: "PENDING"` as notification initiated, not as debit success.
- Continue with the next step only according to your Newton-enabled mandate execution flow.
- If `retryEnabled` was sent and configured, Newton may follow up through Process Tracker. Otherwise use the notification status or execute-cycle status API approved for your integration.

### Successful Duplicate/Idempotent Read

If the same `merchantRequestId` already has a notification in `SUCCESS` or `EXECUTED`, Newton returns the existing notification instead of creating another attempt.

```json
{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "merchantId": "MERCHANT001",
    "merchantChannelId": "APP",
    "merchantRequestId": "NOTIFY000123",
    "originalMerchantRequestId": "MANDATE000123",
    "umn": "12345678901234567890123456789012@upi",
    "nextExecution": "2026-07-04T10:00:00+05:30",
    "amount": "100.00",
    "remarks": "July subscription debit",
    "orgMandateId": "MANDATEUPIREQ000001",
    "gatewayResponseCode": "00",
    "gatewayResponseMessage": "Mandate notification successful",
    "gatewayResponseStatus": "SUCCESS",
    "gatewayTransactionId": "NOTIFYTXN000123",
    "seqNumber": "3"
  }
}
```

Client handling:

- Persist the returned state and do not create another notification for the same cycle.
- If the debit execution still has to be initiated, use the execution API/process agreed for your integration.

### Notification Failure State Returned As Successful API Response

For some NPCI immediate failures, Newton records the notification as failed and still returns a successful API envelope with failure details in the gateway fields.

```json
{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "merchantId": "MERCHANT001",
    "merchantChannelId": "APP",
    "merchantRequestId": "NOTIFY000125",
    "originalMerchantRequestId": "MANDATE000123",
    "umn": "12345678901234567890123456789012@upi",
    "nextExecution": "2026-07-04T10:00:00+05:30",
    "amount": "100.00",
    "remarks": "July subscription debit",
    "orgMandateId": "MANDATEUPIREQ000001",
    "gatewayResponseCode": "U09",
    "gatewayResponseMessage": "Bad Request",
    "gatewayResponseStatus": "FAILURE",
    "gatewayTransactionId": "NOTIFYTXN000125",
    "seqNumber": "3"

```

Client handling:

- Treat the API call as completed but the notification business result as failed.
- Retry with the same `merchantRequestId` only if Newton marks the stored notification retryable or Newton support confirms that retry is allowed.
- For a new cycle, use a new `merchantRequestId`.

## Error Handling

Failure responses use the same top-level error shape after decryption when the response can be enveloped. Some auth, envelope, and middleware errors may be returned before response encryption/signing is possible.

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "RegexValidation \"amount regex match failed\"",
  "payload": null
}
```

### Validation Failures

Request validation errors are returned with `BAD_REQUEST` and a comma-separated validation message.

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "RegexValidation \"amount regex match failed\"",
  "payload": null
}
```

Examples:

- `umn` is too short, too long, or does not match `.{32}@.+`.
- `amount` is not in two-decimal format or is not greater than zero.
- `mandateExecutionTimestamp` cannot be parsed as a timestamp.
- `merchantRequestId` or `originalMerchantRequestId` is longer than 35 characters or contains unsupported characters.
- `upiRequestId` or `orgMandateId` contains non-alphanumeric characters.
- `makeAsync` is not `true` or `false`.
- `payerVpa` or `payeeVpa` is not a valid VPA.
- `udfParameters` is not a JSON-object string or contains disallowed characters.
- `subMerchantDetails` misses required fields or sends only some of `accountNumber`, `ifsc`, and `accountType`.

Client handling:

- Do not retry unchanged.
- Correct the payload and send a new signed/encrypted request.

### Missing `originalMerchantRequestId` For Newer API Versions

For `x-api-version > 1`, Newton rejects requests without `originalMerchantRequestId`.

```json
{
  "status": "FAILURE",
  "responseCode": "INVALID_DATA",
  "responseMessage": "originalMerchantRequestId not found",
  "payload": null
}
```

Client handling:

- Send the mandate creation `merchantRequestId` as `originalMerchantRequestId`.
- Keep `merchantRequestId` as the unique id for this notification cycle.

### Auth, Signature, Encryption, Timestamp, And IP Failures

These failures can occur before product logic and may not be encrypted if Newton cannot authenticate or parse the envelope.

Missing/invalid merchant headers, signature mismatch, missing `iat` for encrypted/signed payloads, invalid `x-timestamp`, or IP whitelist failure commonly return:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "UNAUTHORIZED",
  "payload": null
}
```

If the API is blocked or not allowed for the merchant, Newton returns:

```json
{
  "status": "FAILURE",
  "responseCode": "UNAUTHORIZED",
  "responseMessage": "API NOT ENABLED",
  "payload": null
}
```

Client handling:

- Do not retry with the same signature/timestamps.
- Verify `x-merchant-id`, `x-merchant-channel-id`, optional sub-merchant headers, `x-timestamp`, `iat`, raw-body signing input, and key ids.
- If IP restriction is configured, ensure the first IP in `x-forwarded-for` is allow-listed.
- If the API is disabled, contact Newton onboarding/support to enable `notifyMandate`.

### Mandate Lookup And Configuration Failures

If Newton cannot find the mandate and the request is not a valid interoperability request:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "Mandate not present",
  "payload": null
}
```

If dynamic VPA requirements are not met:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "payee vpa not found",
  "payload": null
}
```

Other dynamic VPA errors include `sub merchant details not found` and `payee vpa not allowed`.

Client handling:

- Verify that the authenticated merchant/sub-merchant owns the mandate.
- Check `umn`, `originalMerchantRequestId`, and `purpose`.
- For interoperability, include all required payer, sequence, initiation-mode, and mandate identifiers.
- For dynamic VPA, align `payeeVpa` and `subMerchantDetails` with the merchant configuration.

### Duplicate And Retry-State Failures

If `executeCycleDetails.initiatedByProcessTracker` is true but no previous notification exists:

```json
{
  "status": "FAILURE",
  "responseCode": "REQUEST_NOT_FOUND",
  "responseMessage": "REQUEST_NOT_FOUND",
  "payload": null
}
```

If a previous notification exists but is not retryable for Process Tracker:

```json
{
  "status": "FAILURE",
  "responseCode": "DUPLICATE_REQUEST",
  "responseMessage": "DUPLICATE_REQUEST",
  "payload": null
}
```

If another valid notification already exists for the same sequence number on a non-`ASPRESENTED` mandate, Newton returns a duplicate/invalid-data style error based on the duplicate check path.

Client handling:

- For merchant-initiated retries, reuse `merchantRequestId` only when the previous notification result is retryable per your Newton configuration.
- For a new execution cycle, use a new `merchantRequestId`.
- Do not send `initiatedByProcessTracker: true` unless Newton has explicitly asked you to do so.

### Downstream NPCI/Gateway Failures

If NPCI/gateway returns an immediate business failure, Newton may return `SUCCESS` at the API level with `payload.gatewayResponseStatus: "FAILURE"` as shown above. If the downstream response is treated as service-unavailable by the validation helper, the decrypted error shape is:

```json
{
  "status": "FAILURE",
  "responseCode": "SERVICE_UNAVAILABLE_NPCI_NA",
  "responseMessage": "NPCI service is not reachable at the moment (NA)",
  "payload": null
}
```

When a timeout/error code is available, it is embedded in `responseCode` and `responseMessage`, for example:

```json
{
  "status": "FAILURE",
  "responseCode": "SERVICE_UNAVAILABLE_NPCI_U09",
  "responseMessage": "NPCI service is not reachable at the moment (U09)",
  "payload": null
}
```

Client handling:

- For transport timeouts or service-unavailable errors, retry with the same `merchantRequestId`, a fresh `iat`, fresh `x-timestamp`, and a freshly computed signature/envelope.
- For API-level `SUCCESS` with `gatewayResponseStatus: "FAILURE"`, use the returned gateway fields and your configured retry policy; do not blindly create another notification.

### Unexpected Internal Errors

Database, Redis, keystore, response encryption/signing, or unexpected application failures can return:

```json
{
  "status": "FAILURE",
  "responseCode": "INTERNAL_SERVER_ERROR",
  "responseMessage": "INTERNAL_SERVER_ERROR",
  "payload": null
}
```

Client handling:

- Retry with the same business payload after a short backoff.
- Use a fresh `iat`, `x-timestamp`, and signature/envelope for every retry.
- If the error persists, contact Newton support with response headers, `x-request-id`, merchant ids, UMN, `merchantRequestId`, and `originalMerchantRequestId`.

## Retry and Idempotency Guidance

- Use one unique `merchantRequestId` per mandate notification cycle.
- Retry network timeouts, HTTP 5xx, `INTERNAL_SERVER_ERROR`, and `SERVICE_UNAVAILABLE_*` with the same `merchantRequestId`.
- Regenerate `iat`, `x-timestamp`, and signatures/envelopes on every retry.
- If you supplied `upiRequestId` and did not receive a definitive response, retry with the same `upiRequestId` unless Newton support advises otherwise. This preserves reconciliation for the notification attempt.
- If the first call succeeded with `gatewayResponseStatus: "PENDING"`, do not create a second notification with a new `merchantRequestId` for the same cycle. Reconcile through the status API or agreed callback/process.
- If the same `merchantRequestId` already maps to `SUCCESS` or `EXECUTED`, Newton returns the existing notification state. Treat that as idempotent success.
- If the same `merchantRequestId` maps to a non-retryable in-progress or failed state, Newton can reject duplicate retry attempts. Use the status API or contact Newton support before retrying manually.
- Do not retry validation, auth, API-disabled, IP restriction, mandate-not-found, invalid amount, invalid timestamp, or invalid mandate-state failures without correcting the request or configuration.
- For a genuinely new cycle, use a new `merchantRequestId`; do not reuse an older cycle id.
