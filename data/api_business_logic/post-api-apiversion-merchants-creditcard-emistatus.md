# EMI Status API Integration Guide

Source endpoint: `POST /api/{apiVersion}/merchants/creditCard/emiStatus`

## Overview

EMI Status is a merchant server-to-server API used after a credit-card EMI selection request has been sent.

The merchant calls this API with the UPI request id returned from, or used for, the earlier `selectEmi` call. Newton sends an NPCI `ReqChkTxn` status check with subtype `EMI` and returns whether the EMI operation has produced an EMI id, is still pending or unresolved, or failed with an issuer/NPCI response code.

Use this API when the merchant backend needs to confirm the final outcome of a credit-card EMI conversion or foreclosure selection before showing the customer a final status, updating the merchant order, or storing the EMI id for later servicing.

## Business Use Case

EMI Status helps merchants:

- Confirm whether a previous `selectEmi` call has successfully created or applied an EMI.
- Retrieve the `emiId` generated by the issuer/NPCI flow.
- Distinguish transport/API success from the actual EMI operation status.
- Poll a post-selection EMI operation that is still pending at the issuer or NPCI.
- Reconcile a merchant-side order or customer journey when the select response was delayed, ambiguous, or did not contain a final EMI id.

Typical credit-card EMI sequence:

1. Merchant calls `checkEmi` to fetch eligible EMI offers or foreclosure details.
2. Merchant calls `selectEmi` after the customer selects an EMI option or foreclosure operation.
3. Merchant calls `emiStatus` with the `selectEmiUpiRequestId` to check whether the selected EMI operation has completed.
4. Newton returns an outer API response and a nested gateway response. Clients should treat the EMI as applied only when the gateway payload contains a successful code and an `emiId`.

## Endpoint

```http
POST /api/{apiVersion}/merchants/creditCard/emiStatus
```

Payloads use the standard Newton server-to-server encrypted/signed request and response envelope. The examples below show the decrypted business payload for readability.

Recommended headers:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `x-api-version` | Use the version shared during onboarding. |
| `x-merchant-id` | Merchant id configured with Newton. |
| `x-merchant-channel-id` | Merchant channel id configured with Newton. |
| `x-timestamp` | Request timestamp used by signature validation. |
| `x-merchant-signature` | Required for checksum/plain-body S2S signature flow. For JWS/JWE flows, use the key and envelope setup shared during onboarding. |
| `x-sub-merchant-id` | Send only when the integration is configured for sub-merchants. |
| `x-sub-merchant-channel-id` | Send only when the integration is configured for sub-merchants. |

Authentication and encryption follow the standard Newton S2S process shared during onboarding. The route first decrypts/verifies the `EncRequest`, resolves the merchant from headers, validates the merchant signature or signed/encrypted payload, checks merchant API access, and then resolves the merchant customer from `merchantCustomerId`. Responses are signed or encrypted according to the merchant's configured response strategy; plain signed responses include `X-Response-Signature` along with `x-requestid` and `x-sessionid` response headers.

## Request

### Required Minimum

Send a unique `upiRequestId` for this status enquiry, the merchant customer id, and the UPI request id of the earlier `selectEmi` call:

```json
{
  "upiRequestId": "EMISTATUS000000000000000001",
  "merchantCustomerId": "CUST12345",
  "selectEmiUpiRequestId": "SELECTEMI000000000000000001"
}
```

### Field Reference

| Field | Type | Required | Default / omitted behavior | Description |
| --- | --- | --- | --- | --- |
| `upiRequestId` | string | Yes | No default. | Merchant-supplied unique id for this EMI status API call. Returned as `payload.gatewayTransactionId`. Must be 1 to 35 alphanumeric characters. |
| `merchantCustomerId` | string | Yes | No default. | Merchant customer/profile id for the customer whose EMI operation is being checked. Newton resolves this profile during signature verification and validates it again in the transformer. |
| `selectEmiUpiRequestId` | string | Yes | No default. | UPI request id of the earlier `selectEmi` call. Newton sends this to NPCI as the original transaction id (`orgTxnId`) for the EMI status check. Must be 1 to 35 alphanumeric characters. |
| `originalTxnTs` | string | No | Omitted from the NPCI `ReqChkTxn` request when not supplied. | Original transaction timestamp, sent as `orgTxnDate` when available or required by the issuer flow. |
| `remarks` | string | No | Defaults to `EmiStatusCheck` in the downstream NPCI request when omitted. | Status-check note. Must be 1 to 255 characters when supplied and match the remarks validation pattern. |
| `purpose` | string | No | Defaults to `00` in the downstream NPCI request when omitted. | UPI purpose code. Must be exactly 2 uppercase alphanumeric characters when supplied. |
| `udfParameters` | string | No | Omitted from response when not supplied. | Merchant-defined metadata as a JSON-object string. Echoed in the top-level response when supplied. |
| `iat` | string | Conditional | No default. | Issued-at timestamp used by signed/encrypted request validation. The type marks it optional, but JWS/JWE requests must include it because middleware validates `iat` for non-plain payloads. |
| `clVersion` | string | No | Omitted from downstream request when not supplied. | Optional client/library version forwarded to NPCI. If supplied, it must be non-empty. |

### Nested Request Objects

This request has no nested business objects.

### Defaults and Omitted Field Behavior

- `remarks`: downstream note defaults to `EmiStatusCheck`.
- `purpose`: downstream purpose defaults to `00`.
- `originalTxnTs`: no default; not sent to NPCI when omitted.
- `clVersion`: no default; not sent to NPCI when omitted.
- `udfParameters`: no processing default; echoed back only when supplied.
- `iat`: no business default. Required for signed/encrypted envelope validation even though it is optional in the business type.

## Response

### Response Envelope

| Field | Type | Description |
| --- | --- | --- |
| `status` | string | Newton API processing status. Success value is `SUCCESS`. This does not by itself mean that the EMI was applied. |
| `responseCode` | string | Newton API response code. Success value is `SUCCESS`. |
| `responseMessage` | string | Newton API response message. |
| `payload` | object | EMI status result. Present for successful Newton processing. |
| `udfParameters` | string | Echoed from request when supplied. Omitted when request did not include it. |

### Payload Fields

| Field | Type | Description |
| --- | --- | --- |
| `gatewayResponseStatus` | string | Status/result returned by the core EMI status check, usually from NPCI `Resp.result` or downstream error handling. Use with `gatewayResponseCode`; do not interpret this field alone. |
| `gatewayResponseCode` | string | Gateway/NPCI or original-transaction response code. `00` with an `emiId` means the EMI operation was successfully applied. If `emiId` is absent, this can be the original transaction response code or an NPCI error code. |
| `gatewayResponseMessage` | string | Message corresponding to `gatewayResponseCode`. For a successful EMI application, Newton returns `Your EMI operation is successfully applied.` |
| `emiId` | string | EMI identifier returned only when the EMI operation has been applied and NPCI/issuer returned an EMI id. Omitted when not available. |
| `gatewayTransactionId` | string | Echo of request `upiRequestId` for this status enquiry. |
| `merchantId` | string | Merchant id configured with Newton. |
| `merchantChannelId` | string | Merchant channel id configured with Newton. |
| `merchantCustomerId` | string | Echo of request `merchantCustomerId`. |

### How to Interpret Status

First check the outer response:

- If outer `status` is `FAILURE`, the request did not complete at the Newton/API layer. Fix the validation, auth, config, or downstream availability issue shown in `responseCode` and `responseMessage`.
- If outer `status` is `SUCCESS`, Newton processed the status enquiry. Then inspect `payload.gatewayResponseCode`, `payload.gatewayResponseStatus`, and `payload.emiId`.

Treat the EMI as applied only when:

- `payload.gatewayResponseCode` is `00`, and
- `payload.emiId` is present.

When `emiId` is absent:

- If `gatewayResponseCode` is `01` or another pending/original-transaction code, keep the order in a pending or unknown state and poll again according to your retry policy.
- If `gatewayResponseCode` is a terminal issuer/NPCI error code, mark the EMI operation as failed according to your business rules and show the mapped failure reason where appropriate.
- If `gatewayResponseStatus` is `FAILURE`, do not treat the outer `SUCCESS` as an EMI success. The nested gateway fields carry the business failure.

{
  "status": "SUCCESS",
  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",
  "payload": {
    "gatewayResponseStatus": "SUCCESS",
    "gatewayResponseCode": "00",
    "gatewayResponseMessage": "Your EMI operation is successfully applied.",
    "emiId": "EMI1234567890",

  "responseCode": "SUCCESS",
  "responseMessage": "SUCCESS",

## Idempotency and Retry Guidance

`emiStatus` is a status enquiry. It does not create the EMI by itself and the code does not maintain a duplicate/idempotency record for the request `upiRequestId`.

Recommended client behavior:

- Use a unique `upiRequestId` for each status enquiry attempt so logs and reconciliation are unambiguous.
- Always send the same `selectEmiUpiRequestId` for the same selected EMI operation.
- Store `selectEmiUpiRequestId`, status-check `upiRequestId`, `gatewayResponseCode`, `gatewayResponseStatus`, and `emiId` when present.
- Retry only when the HTTP call fails, the decrypted outer response is a retryable downstream failure such as `SERVICE_UNAVAILABLE_*`, or the outer response is `SUCCESS` but the nested gateway code indicates pending/unknown status.
- Use bounded backoff and stop polling after the timeout agreed during onboarding or after receiving a terminal gateway code.
- Do not retry validation failures, auth/encryption failures, API-not-enabled errors, merchant/customer lookup failures, or terminal gateway business failures until the underlying issue is corrected.
- If the network drops after sending the request and no response is received, it is safe to send another status enquiry with a new `upiRequestId` and the same `selectEmiUpiRequestId`.

## Error Handling

Failure responses use the same encrypted/signed response transport as successful responses. The examples below show decrypted business bodies.

Most API-layer failures follow this shape:

```json
{
  "status": "FAILURE",
  "responseCode": "BAD_REQUEST",
  "responseMessage": "Validation error"
}
```

The exact `responseCode` and `responseMessage` depend on the validation or business rule that failed. When `payload` is empty, it is omitted from the JSON response. Depending on where the failure occurs, the HTTP status can be `200`, `400`, `401`, or `500`; clients should parse the decrypted body and use `status`, `responseCode`, and `responseMessage` as the integration contract.

### Failure Scenarios

| Scenario | Client handling | Decrypted response body pattern |
| --- | --- | --- |
| Required field is missing or a field has the wrong JSON type | Fix the decrypted business JSON and retry. | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Error in $: key \"upiRequestId\" not present"}` or an HTTP `400` body from the JSON parser, depending on where parsing fails. |
| `upiRequestId` or `selectEmiUpiRequestId` is empty, longer than 35 characters, or non-alphanumeric | Fix the request and retry with valid ids. | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"RegexValidation \"upiRequestId regex match failed\""}` or `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"LengthValidation \"upiRequestId length is not between 1 and 35\""}` |
| `merchantCustomerId` fails format or length validation | Fix the merchant customer id. | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"RegexValidation \"merchantCustomerId is not alphanumeric\""}` |
| `purpose` is not a 2-character uppercase alphanumeric code | Fix or omit `purpose`; omission defaults downstream to `00`. | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"LengthValidation \"Purpose Code length is not 2\""}` |
| `remarks` fails length or regex validation | Fix or omit `remarks`; omission defaults downstream to `EmiStatusCheck`. | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"RegexValidation \"remarks regex match failed\""}` |
| `udfParameters` is not a valid JSON-object string | Send a JSON object serialized as a string, or omit the field. | `{"status":"FAILURE","responseCode":"BAD_REQUEST","responseMessage":"UnexpectedType \"JSON Text parse failed for udfParameters\""}` |
| JWS/JWE request omits `iat` or sends an invalid timestamp | Fix the signed/encrypted payload timestamp. | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Invalid IAT is empty"}` or another timestamp validation message. |
| Missing/invalid merchant headers, missing signature, signature mismatch, failed JWS verification, failed JWE decryption, or IP whitelist failure | Do not retry blindly. Fix credentials, key id, signature, timestamp, encryption, or IP allowlist. | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` |
| Decrypted/signed payload cannot be parsed as the expected business JSON | Fix the envelope payload. | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Error in $: not enough input"}` |
| Merchant exists but the API is blocked or not allowed for the merchant/sub-merchant configuration | Enable the API for the merchant profile before retrying. | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"API NOT ENABLED"}` |
| Merchant id/channel id is unknown | Check onboarding configuration and headers. | `{"status":"FAILURE","responseCode":"UNAUTHORIZED","responseMessage":"UNAUTHORIZED"}` |
| `merchantCustomerId` does not resolve to an active merchant customer | Create/onboard the customer or send the correct id. | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"User profile not found"}` |
| Resolved merchant customer does not match request `merchantCustomerId` | Fix the customer id and merchant context. | `{"status":"FAILURE","responseCode":"INVALID_DATA","responseMessage":"Invalid merchantCustomerId"}` |
| Downstream NPCI/issuer returns an immediate business error for the status enquiry | Treat as a completed status enquiry with failed gateway result; do not rely on the outer `SUCCESS`. | Outer `SUCCESS` with `payload.gatewayResponseStatus = "FAILURE"` and gateway code/message, for example the `C6` response shown above. |
| Downstream NPCI timeout or unreachable service | Retry with backoff. Keep the merchant order in pending/unknown state until a later status check succeeds or terminal timeout is reached. | `{"status":"FAILURE","responseCode":"SERVICE_UNAVAILABLE_NPCI_NA","responseMessage":"NPCI service is not reachable at the moment (NA)"}` |
| Downstream decode failure, missing async response cache entry, database/cache/encryption issue, or unexpected server error | Retry only if your retry policy allows server errors; otherwise escalate with Newton request ids. | `{"status":"FAILURE","responseCode":"INTERNAL_SERVER_ERROR","responseMessage":"INTERNAL_SERVER_ERROR"}` |

### Gateway Codes Commonly Seen in EMI Status

Gateway codes are sourced from NPCI/issuer response codes and Newton's error-code mapping. This list is not exhaustive; clients should store and surface the returned code/message.

| Code | Typical meaning | Client interpretation |
| --- | --- | --- |
| `00` with `emiId` | EMI operation successfully applied. | Mark EMI selection as successful and store `emiId`. |
| `01` without `emiId` | Transaction is pending. | Poll again with backoff. |
| `C1` | Credit card does not exist. | Treat as terminal failure unless issuer guidance says otherwise. |
| `C3` or `C7` | Invalid credit card or card not eligible for EMI. | Treat as terminal failure for the selected card/offer. |
| `C6` or `CX` | Original transaction id mismatch. | Verify `selectEmiUpiRequestId`; do not retry unchanged indefinitely. |
| `C9` | EMI is already created. | Reconcile with prior status/select response; do not create a duplicate merchant success entry. |
| `CE` | Invalid or missing EMI id, or credential crypto issue depending on issuer context. | Treat as terminal or escalate based on the full returned message. |
| `CF` | Foreclosure not possible. | Treat as terminal failure for foreclosure flow. |
| `CM` | MCC not eligible for EMI conversion. | Treat as terminal merchant/category failure. |
| `CP` | Amount not eligible for EMI conversion. | Treat as terminal amount/offer failure. |
